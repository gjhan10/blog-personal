13Módulo 3

REST & HTTP

REST (Representational State Transfer) es un estilo arquitectónico que usa HTTP como protocolo de comunicación. Los conceptos clave son los verbos HTTP, los códigos de estado y las propiedades de seguridad e idempotencia.

GET
Recupera un recurso. Seguro (no modifica estado) e idempotente (repetir produce el mismo resultado). Cacheable. Nunca usar para operaciones que modifiquen datos.
POST
Crea un recurso o ejecuta una operación. No seguro y no idempotente: dos POST iguales crean dos recursos distintos. Devuelve 201 Created con Location header.
PUT
Reemplaza completamente un recurso. No seguro pero idempotente: repetirlo múltiples veces deja el recurso en el mismo estado. Requiere el recurso completo en el body.
PATCH
Actualización parcial de un recurso. No seguro y generalmente no idempotente (depende de la semántica). Solo envía los campos a modificar en el body.
DELETE
Elimina un recurso. No seguro pero idempotente: eliminar un recurso ya eliminado devuelve 404 pero no cambia el estado del servidor de forma diferente.
HEAD & OPTIONS
HEAD: igual que GET pero sin body en la respuesta. Idempotente y seguro. OPTIONS: devuelve los métodos permitidos. Base del preflight CORS. Seguro e idempotente.
Seguro (Safe)
No modifica el estado del servidor
Solo lectura
Métodos: GET, HEAD, OPTIONS
Cacheable por proxies y navegadores
Idempotente
Repetir N veces = resultado igual a 1 vez
No implica que sea seguro
Métodos: GET, HEAD, PUT, DELETE, OPTIONS
POST y PATCH NO son idempotentes
2xx
Éxito: 200 OK, 201 Created, 204 No Content, 206 Partial Content.
3xx
Redirección: 301 Moved Permanently, 302 Found, 304 Not Modified.
4xx
Error cliente: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity.
5xx
Error servidor: 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.
// Mapa de verbo → operación CRUD
GET /productos → listar todos (200)
GET /productos/{{ '{' }}id{{ '}' }} → obtener uno (200 / 404)
POST /productos → crear (201 + Location)
PUT /productos/{{ '{' }}id{{ '}' }} → reemplazar (200 / 204)
PATCH /productos/{{ '{' }}id{{ '}' }} → actualizar parcial (200)
DELETE /productos/{{ '{' }}id{{ '}' }} → eliminar (204 / 404)
La idempotencia es una garantía del cliente, no del servidor. Si el servidor no la implementa correctamente (ej. POST duplicado sin clave de idempotencia), la responsabilidad recae en el diseño de la API.

@RestController

@RestController combina @Controller y @ResponseBody. Todos los métodos del controlador devuelven datos directamente en el cuerpo HTTP, serializados por Jackson a JSON (o XML) según la negociación de contenido.

@GetMapping
Atajo de @RequestMapping(method=GET). Mapea peticiones HTTP GET a un método del controlador. El más frecuente en APIs REST de solo lectura.
@PostMapping
Atajo de @RequestMapping(method=POST). Crea recursos. El método debe devolver 201 Created con el recurso creado y el header Location apuntando al nuevo recurso.
@PutMapping / @PatchMapping
Atajos para PUT y PATCH respectivamente. PUT reemplaza el recurso completo. PATCH aplica una modificación parcial. Ambos requieren el id en la URL.
@DeleteMapping
Atajo para DELETE. Normalmente devuelve 204 No Content sin body al eliminar con éxito, o 404 Not Found si el recurso no existe.
Content Negotiation
Spring elige el HttpMessageConverter según el header Accept del cliente y el atributo produces del mapping. Por defecto application/json via Jackson.
@CrossOrigin
Habilita CORS a nivel de controlador o método. Configura los orígenes permitidos, métodos, headers y tiempo de caché del preflight. Alternativa global: CorsConfigurationSource en SecurityFilterChain.

  @PostMapping // POST /api/v1/productos

  public ProductoDTO crear(@RequestBody ProductoDTO dto) {{ '{' }} ... {{ '}' }}

Devuelve nombre de vista (String)
El resolver busca la plantilla HTML
@ResponseBody necesario para JSON
Úsalo con Thymeleaf / FreeMarker

@PathVariable & @RequestParam

Spring MVC permite capturar valores de la URL de tres formas: variables de path (@PathVariable), parámetros de query (@RequestParam) y cabeceras HTTP (@RequestHeader). Cada una tiene semántica y casos de uso distintos.

@PathVariable
Extrae un segmento de la URL. /usuarios/{{ '{' }}id{{ '}' }} → @PathVariable Long id. Es obligatorio por defecto. Puede ser opcional con required=false usando Optional<T>.
@RequestParam
Extrae un parámetro de query string. ?pagina=2&tamaño=10 → @RequestParam(defaultValue="0") int pagina. Con required=false y defaultValue puede ser opcional.
@RequestHeader
Extrae una cabecera HTTP. @RequestHeader("X-Tenant-Id") String tenantId. Útil para multi-tenancy, tokens de correlación y negociación de versión por header.
@MatrixVariable
Extrae variables de matriz de un segmento de path: /carros/color=rojo;marca=ford. Menos común, requiere activar removeSemicolonContent=false en la configuración MVC.
// @PathVariable — segmento de URL
@GetMapping("/usuarios/{{ '{' }}id{{ '}' }}/pedidos/{{ '{' }}pedidoId{{ '}' }}")
public PedidoDTO getPedido(
    @PathVariable Long id,
    @PathVariable Long pedidoId) {{ '{' }} ... {{ '}' }}
// @RequestParam — query string con defecto
@GetMapping("/productos")
public Page<ProductoDTO> listar(
    @RequestParam(defaultValue = "0") int pagina,
    @RequestParam(defaultValue = "20") int tamaño,
    @RequestParam(required = false) String buscar) {{ '{' }} ... {{ '}' }}
// @RequestHeader — cabecera HTTP
@GetMapping("/datos")
public ResponseEntity<DatosDTO> getDatos(
    @RequestHeader("X-Api-Version") String version,
    @RequestHeader(value = "X-Tenant", required = false) String tenant) {{ '{' }} ... {{ '}' }}

@RequestParam — filtro / paginación

/pedidos?estado=pendiente&pagina=2
Modifica la colección devuelta
Opcional con valores por defecto
Cuando el nombre del parámetro Java coincide con el nombre en la URL puedes omitir el valor: @PathVariable Long id en lugar de @PathVariable("id") Long id. Solo funciona si el código se compila con -parameters (por defecto en Spring Boot).

@RequestBody & DTOs

@RequestBody instruye a Spring para deserializar el cuerpo HTTP en un objeto Java usando Jackson. El patrón DTO (Data Transfer Object) separa la API pública de las entidades de dominio, evitando exponer detalles de persistencia.

@RequestBody
Lee el body de la petición HTTP y lo deserializa al tipo Java indicado. Requiere Content-Type: application/json. Jackson mapea automáticamente camelCase JSON a campos Java.
Patrón DTO
Clase simple que representa lo que el cliente envía o recibe. Desacopla la API del modelo de dominio: puedes cambiar la base de datos sin afectar el contrato de la API.
Record DTOs (Java 16+)
record ProductoRequest(String nombre, BigDecimal precio) {{ '{' }}{{ '}' }}. Inmutable, conciso, genera equals/hashCode/toString. Jackson los serializa/deserializa automáticamente desde Spring Boot 2.7.
Jackson Config
@JsonProperty("nombre_campo") mapea nombres distintos. @JsonIgnore excluye campos sensibles. @JsonFormat formatea fechas. Configura globalmente en ObjectMapper bean.
// DTO clásico (class)
public class ProductoRequest {{ '{' }}

  private BigDecimal precio;
  // getters / setters
{{ '}' }}
// DTO moderno (record)
public record ProductoRequest(
  @JsonProperty("nombre_producto") String nombre,
  BigDecimal precio) {{ '{' }}{{ '}' }}
// Endpoint usando el DTO
@PostMapping
public ResponseEntity<ProductoResponse> crear(
    @RequestBody ProductoRequest request) {{ '{' }}
  ProductoResponse resp = service.crear(request);
  return ResponseEntity.created(location(resp.id())).body(resp);
{{ '}' }}
Exponer la entidad JPA directamente
Acopla API con esquema de BBDD
Riesgo de serialización infinita (bidireccionales)
Campos sensibles expuestos (@Password)
Cambios de BBDD rompen la API
DTO separado de la entidad
Contrato de API estable e independiente
Solo los campos necesarios para el cliente
Validaciones específicas de la API
Mapeo explícito (MapStruct / manual)
Si el JSON no puede deserializarse al tipo esperado, Jackson lanza HttpMessageNotReadableException y Spring responde automáticamente con 400 Bad Request. No necesitas try-catch: manéjalo en un @ExceptionHandler global.

Bean Validation

Bean Validation (Jakarta Validation 3.x) permite anotar DTOs con restricciones declarativas. @Valid en el parámetro del controlador activa la validación automática. Los errores se capturan con MethodArgumentNotValidException.

@NotNull / @NotBlank
@NotNull: el valor no puede ser null. @NotBlank: String no puede ser null, vacío ni solo espacios. Usa @NotBlank para cadenas de texto en lugar de @NotNull.
@Size / @Min / @Max
@Size(min=2, max=100): longitud de String, array, colección. @Min(0) / @Max(9999): rango numérico. @DecimalMin / @DecimalMax para BigDecimal.
@Email / @Pattern
@Email: valida formato de correo electrónico. @Pattern(regexp="..."): valida contra expresión regular. Ambas aplican solo si el valor no es null (@NotNull es independiente).
@Positive / @Future
@Positive / @PositiveOrZero: números positivos. @Past / @Future: fechas en el pasado o futuro. @PastOrPresent para fechas de nacimiento.

  @NotBlank(message = "El nombre es obligatorio")

  String nombre,
  @NotNull
  @DecimalMin("0.01")
  BigDecimal precio,
  @Email
  String emailProveedor) {{ '{' }}{{ '}' }}
// Activar validación en el controlador
@PostMapping
public ResponseEntity<ProductoDTO> crear(
    @Valid @RequestBody ProductoRequest req) {{ '{' }} ... {{ '}' }}
1
Spring MVC recibe la petición y deserializa el body a ProductoRequest con Jackson.
2
Al ver @Valid, Spring delega en el Validator de Jakarta para comprobar todas las restricciones.
3
Si hay violaciones, lanza MethodArgumentNotValidException antes de entrar al método.
4
El @ExceptionHandler captura la excepción y construye la respuesta 400 con los detalles de los errores de campo.
@Valid (JSR-303)
Activación básica de validación
Usa el Validator por defecto
Solo en parámetros de método
No soporta grupos de validación
@Validated (Spring)
Extiende @Valid con grupos
@Validated({{ '{' }}Create.class{{ '}' }}) para flujos distintos
Funciona en @Service (métodos de servicio)
Permite validaciones condicionales por contexto
BindingResult como parámetro inmediatamente después de @Valid captura los errores de validación sin lanzar excepción. Úsalo cuando quieras manejar los errores manualmente dentro del método del controlador.
18Módulo 3

@ExceptionHandler & @ControllerAdvice

@ExceptionHandler captura excepciones lanzadas dentro de un controlador. @ControllerAdvice extiende ese manejo a toda la aplicación. Spring Boot 3 introduce ProblemDetail conforme al RFC 9457.

@ExceptionHandler local
Método dentro del propio controlador. Solo captura excepciones del mismo controlador. El método recibe la excepción como parámetro y devuelve la respuesta apropiada.
@ControllerAdvice global
Clase anotada con @ControllerAdvice o @RestControllerAdvice. Sus @ExceptionHandler aplican a todos los controladores. Centraliza el manejo de errores.
ProblemDetail (RFC 9457)
Formato estándar para respuestas de error en APIs HTTP. Campos: type, title, status, detail, instance. Spring Boot 3 lo soporta nativamente con ProblemDetail.forStatus().
ResponseEntityExceptionHandler
Clase base que maneja las excepciones estándar de Spring MVC (MethodArgumentNotValidException, HttpMessageNotReadableException, etc.). Extiéndela para personalizar esas respuestas.
@RestControllerAdvice
public class GlobalExceptionHandler
    extends ResponseEntityExceptionHandler {{ '{' }}
  @ExceptionHandler(RecursoNoEncontradoException.class)
  public ProblemDetail handleNotFound(RecursoNoEncontradoException ex,
      HttpServletRequest req) {{ '{' }}
    ProblemDetail pd = ProblemDetail
      .forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    pd.setType(URI.create("https://api.example.com/errors/not-found"));
    pd.setInstance(URI.create(req.getRequestURI()));
    return pd;
  {{ '}' }}
  @Override
  protected ResponseEntity<Object> handleMethodArgumentNotValid(
      MethodArgumentNotValidException ex, ...) {{ '{' }}
    ProblemDetail pd = ProblemDetail.forStatus(422);
    pd.setProperty("errors", buildErrors(ex.getBindingResult()));
    return ResponseEntity.unprocessableEntity().body(pd);
  {{ '}' }}
{{ '}' }}
1
El controlador lanza una excepción (negocio, validación, etc.).
2
Spring busca un @ExceptionHandler en el propio controlador primero.
3
Si no existe, busca en las clases @ControllerAdvice registradas en el contexto.
4
El handler construye la respuesta de error (ProblemDetail, JSON custom, etc.).
5
Si no hay ningún handler, DefaultHandlerExceptionResolver devuelve 500.
Si hay múltiples clases @ControllerAdvice, usa @Order(1) para controlar la precedencia. Sin orden, Spring los aplica en orden de registro del bean, lo que puede ser impredecible.
19Módulo 3

ResponseEntity

ResponseEntity<T> es la respuesta HTTP completa: código de estado, headers y body. Proporciona control total sobre la respuesta y es preferible a @ResponseStatus cuando necesitas ajustar headers dinámicamente.

API Fluida
ResponseEntity.ok(body), .created(uri), .noContent(), .notFound(). El método estático devuelve un BodyBuilder al que se encadenan .header(), .contentType() y .body().
HttpHeaders
Clase que encapsula los headers HTTP. Permite añadir Location, Content-Disposition, Cache-Control, ETag, etc. Usada con ResponseEntity.headers(headers).body(body).
HttpStatus enum
HttpStatus.OK (200), CREATED (201), NO_CONTENT (204), BAD_REQUEST (400), NOT_FOUND (404), UNPROCESSABLE_ENTITY (422). Úsalo sobre valores literales enteros.
vs @ResponseStatus
@ResponseStatus es estático: fija el código en compile-time. ResponseEntity es dinámico: el código depende de la lógica (ej. 200 si actualizado, 201 si creado, 204 si eliminado).
// GET — 200 OK con body / 404 Not Found
@GetMapping("/{{ '{' }}id{{ '}' }}")
public ResponseEntity<ProductoDTO> get(@PathVariable Long id) {{ '{' }}
  return service.findById(id)
    .map(ResponseEntity::ok)
    .orElse(ResponseEntity.notFound().build());
{{ '}' }}
// POST — 201 Created con Location header
@PostMapping
public ResponseEntity<ProductoDTO> crear(
    @Valid @RequestBody ProductoRequest req,
    UriComponentsBuilder ucb) {{ '{' }}
  ProductoDTO creado = service.crear(req);
  URI location = ucb.path("/api/v1/productos/{{ '{' }}id{{ '}' }}")
    .buildAndExpand(creado.id()).toUri();
  return ResponseEntity.created(location).body(creado);
{{ '}' }}
// DELETE — 204 No Content
@DeleteMapping("/{{ '{' }}id{{ '}' }}")
public ResponseEntity<Void> eliminar(@PathVariable Long id) {{ '{' }}
  service.eliminar(id);
  return ResponseEntity.noContent().build();
{{ '}' }}
@ResponseStatus (estático)
Código fijo en tiempo de compilación
No permite headers dinámicos
Código más limpio para casos simples
No se puede cambiar según la lógica
ResponseEntity (dinámico)
Código según la lógica de negocio
Headers dinámicos (Location, ETag, etc.)
Control total sobre la respuesta HTTP
Recomendado para APIs REST complejas
ResponseEntity.BodyBuilder admite encadenar múltiples llamadas: ResponseEntity.status(201).contentType(MediaType.APPLICATION_JSON).header("X-Custom","valor").body(dto). El body es el último paso: cierra el builder.
