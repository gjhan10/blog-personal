32 Módulo 6 · Testing JUnit 5 con Spring
@Test · @BeforeEach/@AfterEach · @BeforeAll/@AfterAll · assertThrows · @ParameterizedTest · @ExtendWith
@Test
Anotación principal de JUnit 5 (Jupiter). Marca un método como caso de prueba. No requiere modificadores de acceso específicos. Puede ser void o retornar cualquier tipo que JUnit ignore.
@BeforeEach / @AfterEach
@BeforeEach se ejecuta antes de cada método @Test. Ideal para inicializar objetos. @AfterEach se ejecuta después de cada test para limpiar recursos. Ambos se llaman por cada instancia de la clase de test.
@BeforeAll / @AfterAll
@BeforeAll se ejecuta una sola vez antes de todos los tests de la clase. Debe ser static (salvo con @TestInstance(Lifecycle.PER_CLASS)). Útil para configuración costosa como levantar servidores o conexiones.
assertThrows
assertThrows(ExceptionClass.class, () -> codigo()) verifica que el bloque lanza la excepción esperada. Retorna la instancia de la excepción para hacer asserts adicionales sobre su mensaje o causa.
@ParameterizedTest
Ejecuta el mismo test con múltiples valores. Con @ValueSource se proveen valores literales (ints, strings, etc.). Con @MethodSource se referencia un método estático que devuelve un Stream de argumentos.
@ExtendWith(SpringExtension.class)
Integra JUnit 5 con el ApplicationContext de Spring. Carga el contexto y permite inyección de dependencias en las clases de test. Es equivalente a @RunWith(SpringRunner.class) de JUnit 4. Incluido implícitamente en @SpringBootTest.
@ExtendWith(SpringExtension.class)
class ProductServiceTest {{ '{' }}
  @BeforeAll
  static void initAll() {{ '{' }} /* una vez */ {{ '}' }}
  @BeforeEach
  void init() {{ '{' }} /* antes de cada @Test */ {{ '}' }}
  @Test
  void shouldThrowWhenNotFound() {{ '{' }}
    RuntimeException ex = assertThrows(RuntimeException.class,
      () -> service.findById(-1L));
    assertEquals("Not found", ex.getMessage());
  {{ '}' }}
  @ParameterizedTest
  @ValueSource(ints = {{ '{' }}1, 2, 3{{ '}' }})
  void shouldFindById(int id) {{ '{' }}
    assertNotNull(service.findById((long) id));
  {{ '}' }}
{{ '}' }}
@MethodSource admite métodos en la misma clase (sin nombre completo) o en clases externas usando el formato "com.pkg.Clase#metodo". El método debe ser static y devolver Stream, Iterable, Iterator o array.
33 Módulo 6 · Testing Mockito
@Mock vs @MockBean · @InjectMocks · when/thenReturn · verify · ArgumentCaptor · @Spy vs @SpyBean · doThrow
@Mock vs @MockBean
@Mock (Mockito puro) crea un mock sin Spring Context. Vive solo en la prueba unitaria. @MockBean (Spring Boot Test) crea un mock y lo registra como bean en el ApplicationContext de Spring, reemplazando el bean real. Úsalo cuando necesites el contexto de Spring.
@InjectMocks
Le dice a Mockito que cree una instancia de la clase bajo prueba e inyecte en ella los mocks y spies declarados con @Mock / @Spy. Requiere MockitoAnnotations.openMocks(this) o la extensión @ExtendWith(MockitoExtension.class).
when().thenReturn()
Define el comportamiento de un mock: when(repo.findById(1L)).thenReturn(Optional.of(producto)). Variantes: thenThrow() lanza excepción, thenAnswer() ejecuta lógica dinámica, thenCallRealMethod() llama al método real.
verify()
Comprueba que un método fue invocado. verify(repo).save(any()) falla si el método no fue llamado. Con times(n), never(), atLeastOnce() se controla el número de invocaciones. verifyNoMoreInteractions() asegura que no haya otras llamadas.
ArgumentCaptor
Captura los argumentos pasados a un mock para inspeccionarlos. ArgumentCaptor<Product> captor = ArgumentCaptor.forClass(Product.class). Después de verify(repo).save(captor.capture()), se accede al valor con captor.getValue().
@Spy vs @SpyBean
@Spy (Mockito) envuelve un objeto real y solo intercepta los métodos que se configuran explícitamente; el resto llaman al código real. @SpyBean (Spring Boot Test) hace lo mismo pero con un bean del ApplicationContext, combinando comportamiento real con stubbing selectivo.
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {{ '{' }}
  @Mock OrderRepository repo;
  @InjectMocks OrderService service;
  @Test
  void captureArgument() {{ '{' }}
    ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
    service.create(new OrderDto("item", 5));
    verify(repo).save(captor.capture());
    assertEquals(5, captor.getValue().getQuantity());
  {{ '}' }}
  @Test
  void shouldPropagateException() {{ '{' }}
    doThrow(new RuntimeException("DB down")).when(repo).save(any());
    assertThrows(RuntimeException.class, () -> service.create(new OrderDto()));
  {{ '}' }}
{{ '}' }}
@Mock — sin contexto Spring
@ExtendWith(MockitoExtension.class) @Mock UserRepository repo; // Mock vive solo en esta clase
@MockBean — reemplaza bean Spring
@SpringBootTest @MockBean UserRepository repo; // Bean del contexto reemplazado
doThrow() es necesario en lugar de when().thenThrow() cuando el método que lanza la excepción es void. Para métodos con retorno, ambas formas funcionan.
34 Módulo 6 · Testing MockMvc
MockMvc setup · perform · andExpect · status · jsonPath · contentType · @AutoConfigureMockMvc · MockMvcRequestBuilders
¿Qué es MockMvc?
MockMvc permite probar controladores Spring MVC sin levantar un servidor HTTP real. Simula el ciclo completo request/response a nivel de DispatcherServlet: filtros, interceptores, validación, serialización JSON y manejo de excepciones.
Setup
Se instancia con MockMvcBuilders.standaloneSetup(controller) (sin contexto) o vía @AutoConfigureMockMvc + @SpringBootTest (contexto completo). Con @WebMvcTest se carga solo la capa web sin persistencia.
perform()
Ejecuta una request simulada. Recibe un MockHttpServletRequestBuilder construido con MockMvcRequestBuilders.get("/ruta"), .post(), .put(), .delete(), etc. Admite headers, params, content y contentType.
andExpect()
Encadena assertions sobre la respuesta. status().isOk() verifica HTTP 200, status().isNotFound() verifica 404. jsonPath("$.name") navega el JSON de respuesta con expresiones JSONPath. content().contentType() verifica el Content-Type.
jsonPath()
Utiliza la librería JsonPath para navegar el cuerpo JSON. .value("Alice") comprueba igualdad, .exists() comprueba presencia, .isArray() valida el tipo, .hasJsonPathValue("$.items[0].id") para rutas anidadas.
@AutoConfigureMockMvc
Combinado con @SpringBootTest, crea y configura automáticamente un MockMvc con toda la cadena de filtros y seguridad del contexto. Admite addFilters = false para desactivar filtros. Permite inyectar MockMvc con @Autowired.
@SpringBootTest
@AutoConfigureMockMvc
class ProductControllerTest {{ '{' }}
  @Autowired MockMvc mockMvc;
  @MockBean ProductService service;
  @Test
  void getProductReturns200() throws Exception {{ '{' }}
    when(service.findById(1L)).thenReturn(new Product(1L, "Laptop"));
    mockMvc.perform(MockMvcRequestBuilders.get("/api/products/1")
        .accept(MediaType.APPLICATION_JSON))
      .andExpect(status().isOk())
      .andExpect(content().contentType(MediaType.APPLICATION_JSON))
      .andExpect(jsonPath("$.name").value("Laptop"))
      .andExpect(jsonPath("$.id").value(1));
  {{ '}' }}
{{ '}' }}
Para tests más rápidos usa @WebMvcTest(ProductController.class): carga solo la capa web (controladores, filtros, convertidores) sin JPA ni servicios completos. Los beans de servicio deben mockearse con @MockBean.
35 Módulo 6 · Testing @SpringBootTest
webEnvironment · TestRestTemplate · @MockBean en contexto · @TestConfiguration · Slices
@SpringBootTest
Carga el ApplicationContext completo de Spring Boot para pruebas de integración. Escanea desde la clase anotada con @SpringBootApplication y levanta todos los beans, configuraciones y autoconfigurations.
webEnvironment
MOCK (default): contexto web simulado, sin servidor real. RANDOM_PORT: levanta servidor en puerto aleatorio (evita conflictos). DEFINED_PORT: usa el puerto configurado (server.port). NONE: sin capa web.
TestRestTemplate
Cliente HTTP simplificado para tests de integración con servidor real (RANDOM_PORT/DEFINED_PORT). No lanza excepciones en errores HTTP (retorna ResponseEntity). Se inyecta con @Autowired cuando el servidor está activo. Maneja cookies y redirects automáticamente.
@MockBean en contexto
Con @SpringBootTest, @MockBean reemplaza el bean real en el ApplicationContext por un mock de Mockito. Esto invalida el caché del contexto, forzando la recarga del contexto en los tests que lo usan. Úsalo con moderación para preservar el rendimiento.
@TestConfiguration
Define beans adicionales o de reemplazo exclusivamente para tests. A diferencia de @Configuration normal, no es detectada por el escaneo de componentes principal. Se puede anidar dentro de la clase de test o importar con @Import. Ideal para configurar datasources en memoria, mocks específicos o beans de test.
Test Slices
Spring Boot ofrece slices especializados que cargan solo parte del contexto: @WebMvcTest (capa web), @DataJpaTest (JPA), @JsonTest (serialización), @WebFluxTest (Reactive), @RestClientTest (clientes REST). Son más rápidos que @SpringBootTest completo.
RANDOM_PORT
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT) // Puerto aleatorio → sin conflictos @LocalServerPort int port;
DEFINED_PORT
@SpringBootTest(webEnvironment = WebEnvironment.DEFINED_PORT) // Usa server.port (default 8080) // Puede fallar si el puerto está ocupado
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class OrderIntegrationTest {{ '{' }}
  @Autowired TestRestTemplate restTemplate;
  @MockBean EmailService emailService; // reemplaza bean real
  @TestConfiguration
  static class TestConfig {{ '{' }}
    @Bean
    Clock fixedClock() {{ '{' }} return Clock.fixed(Instant.EPOCH, ZoneOffset.UTC); {{ '}' }}
  {{ '}' }}
  @Test
  void createOrderReturns201() {{ '{' }}
    ResponseEntity<Order> resp = restTemplate.postForEntity("/api/orders", dto, Order.class);
    assertEquals(HttpStatus.CREATED, resp.getStatusCode());
  {{ '}' }}
{{ '}' }}
Cada combinación única de configuración del contexto (diferente @MockBean, @TestPropertySource, etc.) genera un nuevo ApplicationContext. Minimiza variaciones para aprovechar el caché de contexto y acelerar la suite de tests.
36 Módulo 6 · Testing @DataJpaTest
H2 auto-configured · TestEntityManager · @Sql · @Rollback · Test isolation · @AutoConfigureTestDatabase
@DataJpaTest
Slice de test que carga únicamente la capa JPA: entidades, repositorios, Hibernate y la base de datos. Excluye controladores, servicios y otras configuraciones. Configura automáticamente una base de datos en memoria H2 y gestiona transacciones por test.
H2 Auto-configurado
Spring Boot sustituye la datasource real por H2 en memoria cuando se usa @DataJpaTest (comportamiento de @AutoConfigureTestDatabase con Replace.ANY por defecto). El esquema se genera desde las entidades JPA con ddl-auto=create-drop.
TestEntityManager
Wrapper de EntityManager diseñado para tests. Ofrece métodos simplificados: persist(entity), find(Class, id), flush(), persistAndFlush(entity). Permite controlar el estado del contexto de persistencia explícitamente durante los tests.
@Sql
Ejecuta scripts SQL antes o después de un test. Puede anotarse en la clase o en métodos específicos. @Sql("/data.sql") carga datos de prueba. @Sql(scripts = "/cleanup.sql", executionPhase = AFTER_TEST_METHOD) limpia después del test.
@Rollback
Por defecto, @DataJpaTest envuelve cada test en una transacción que hace rollback automático al finalizar, garantizando aislamiento. Con @Rollback(false) o @Commit se persisten los cambios. Útil para depurar el estado real de la BD.
@AutoConfigureTestDatabase
Personaliza la sustitución de datasource. replace = Replace.NONE usa la datasource de producción (útil con Testcontainers). replace = Replace.AUTO_CONFIGURED solo reemplaza datasources auto-configuradas. Permite combinar @DataJpaTest con bases de datos reales en CI.
@DataJpaTest
@Sql("/test-data/products.sql")
class ProductRepositoryTest {{ '{' }}
  @Autowired TestEntityManager em;
  @Autowired ProductRepository repo;
  @Test
  void findByCategory() {{ '{' }}
    Product p = em.persistAndFlush(new Product("Teclado", "TECH"));
    List<Product> results = repo.findByCategory("TECH");
    assertThat(results).contains(p);
  {{ '}' }}
  @Test
  @Rollback(false)
  void persistsForDebug() {{ '{' }}
    repo.save(new Product("Monitor", "TECH"));
    // datos visibles en BD para inspección
  {{ '}' }}
{{ '}' }}
1Añade la dependencia H2 en scope test en pom.xml / build.gradle
2Usa @DataJpaTest para cargar solo la capa JPA y reducir tiempo de arranque
3Usa TestEntityManager.persistAndFlush() para insertar datos y forzar el flush al contexto de persistencia antes de llamar al repositorio
4Para tests contra BD real usa @AutoConfigureTestDatabase(replace = Replace.NONE) + Testcontainers
@DataJpaTest no carga @Service ni @Controller. Si tu repositorio tiene dependencias en otros beans, inyéctalos manualmente con @Import o usa @SpringBootTest con el slice adecuado.

A@Mock usa reflexión; @MockBean usa proxies JDK

¿Cómo funciona el caché del contexto de Spring en pruebas y qué lo invalida?
AEl contexto se recrea para cada clase de test siempre
BSpring reutiliza el mismo contexto entre tests con la misma configuración; @MockBean, @DirtiesContext o @TestPropertySource diferente invalidan el caché
CEl contexto solo se cachea cuando se usa @SpringBootTest(webEnvironment=NONE)

Incorrecto. Spring reutiliza el ApplicationContext entre tests con idéntica configuración. @MockBean, @DirtiesContext y cambios en propiedades de test invalidan ese caché y fuerzan la recarga del contexto.

Incorrecto. @DirtiesContext marca el contexto como "sucio" y hace que Spring lo descarte y recargue para los tests siguientes. Se usa cuando un test altera el estado del ApplicationContext de forma que afectaría otros tests.

¿Qué ventaja ofrece assertAll() de JUnit 5 frente a assertions individuales?
AEs más rápido que assertEquals porque no usa reflexión
BEjecuta todas las assertions agrupadas aunque algunas fallen, reportando todos los fallos a la vez en lugar de detenerse en el primero
CPermite reutilizar los mismos assertions en múltiples tests automáticamente
DAgrupa los tests en suites y ejecuta cada assertion en un thread separado
Correcto. assertAll() garantiza que todas las assertions del grupo se evalúan siempre, reportando todos los fallos en un solo informe. Con assertions individuales, el test se detiene en la primera que falla, ocultando el resto de problemas.
Incorrecto. assertAll() evalúa todas las assertions del grupo aunque algunas fallen, lo que permite ver de una sola ejecución todos los problemas en lugar de tener que corregirlos uno a uno ejecutando el test repetidamente.

¿Cuándo deberías usar TestEntityManager en lugar de JpaRepository en un test @DataJpaTest?
APara preparar el estado inicial de la BD (arrange) sin pasar por la lógica del repositorio bajo prueba, garantizando que el setup no está contaminado por el código que se quiere testear
BTestEntityManager siempre debe usarse; JpaRepository no está disponible en @DataJpaTest
CSolo se usa TestEntityManager cuando la entidad no tiene un repositorio definido
DTestEntityManager es más rápido porque evita la capa de abstracción de Spring Data
Correcto. El patrón recomendado es usar TestEntityManager para el arrange (insertar datos de prueba) y JpaRepository para el act/assert (ejecutar y verificar la query bajo prueba). Así el setup no depende del código que se está probando.
Incorrecto. La práctica recomendada es usar TestEntityManager para insertar datos de prueba (arrange) y el JpaRepository bajo prueba para el act/assert. Esto evita que el código de setup y el código bajo prueba sean el mismo, haciendo el test más fiable.

¿Qué problema puede ocurrir cuando múltiples clases de test usan @MockBean sobre el mismo bean?
AEl bean mockeado lanza NullPointerException en el segundo test
B@MockBean solo puede usarse una vez por proyecto; el segundo uso falla en compilación
CCada combinación diferente de @MockBean genera un contexto separado, aumentando el tiempo de ejecución; además, si un test deja el mock en estado inesperado y el contexto se reutiliza, puede contaminar otros tests
DSolo puede haber un @MockBean por tipo en todo el contexto; el segundo sobrescribe silenciosamente al primero
Correcto. Cada configuración única de @MockBean crea un nuevo ApplicationContext, lo que puede multiplicar el tiempo de arranque en suites grandes. Además, si el contexto se reutiliza entre tests y el mock no se reinicia (sin @ResetMocks), el estado puede contaminar otros tests.
Incorrecto. El problema real de @MockBean en múltiples tests es doble: cada configuración diferente invalida el caché del contexto (más tiempo de arranque), y si el contexto se comparte sin resetear el mock, el estado de un test puede afectar a los siguientes.
