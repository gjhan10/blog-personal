07Módulo 2

Contenedor IoC

El contenedor IoC (Inversion of Control) de Spring gestiona la creación, configuración y ciclo de vida de los objetos (beans). BeanFactory es la interfaz base; ApplicationContext la extiende con soporte de eventos, i18n y más.

BeanFactory
Interfaz raíz del contenedor
Instanciación lazy por defecto
No soporta eventos de contexto
No soporta i18n
No registra BeanPostProcessors automáticamente
Uso: entornos con restricciones de memoria
ApplicationContext
Extiende BeanFactory
Instanciación eager por defecto
Publica y consume ApplicationEvents
Soporte i18n con MessageSource
Registra BeanPostProcessors automáticamente
Uso: aplicaciones Spring Boot (siempre)
Fase Init
El contenedor instancia el bean, inyecta dependencias y ejecuta callbacks de inicialización: @PostConstruct, InitializingBean.afterPropertiesSet(), initMethod.
Fase Use
El bean está listo para ser usado. En scope singleton vive mientras dura el contexto. En prototype, Spring entrega la instancia y pierde el control.
Fase Destroy
Al cerrar el contexto se ejecutan: @PreDestroy, DisposableBean.destroy(), destroyMethod. Solo aplica a beans singleton.
@Bean
Declara un método en una clase @Configuration como proveedor de un bean. Spring intercepta la llamada al método para garantizar el singleton.
@Configuration
public class AppConfig {{ '{' }}
  @Bean(initMethod = "init", destroyMethod = "cleanup")
  public DataService dataService() {{ '{' }}
    return new DataService();
  {{ '}' }}
{{ '}' }}
1
Spring lee la metadata de definición de beans (anotaciones o XML).
2
Los BeanFactoryPostProcessor modifican la metadata antes de instanciar beans.
3
El contenedor instancia los beans en orden de dependencia.
4
Los BeanPostProcessor envuelven los beans (AOP, validación, etc.).
5
Se ejecutan los callbacks @PostConstruct e InitializingBean.
6
La aplicación usa los beans normalmente.
7
Al cerrar: @PreDestroy y DisposableBean.destroy().
AnnotationConfigApplicationContext es el ApplicationContext estándar para aplicaciones basadas en anotaciones. Spring Boot lo gestiona internamente con SpringApplication.run().
08Módulo 2

Beans & Estereotipos

Spring define cuatro estereotipos de componentes. Todos son especializaciones de @Component y activan el escaneo automático, pero transmiten semántica adicional y habilitan funcionalidades específicas.

@Component
Estereotipo genérico. Úsalo cuando ninguna otra anotación semántica es apropiada: utilidades, helpers, adaptadores. Es la base de los demás estereotipos.
@Service
Marca la lógica de negocio. Semánticamente indica que la clase contiene operaciones de servicio. Habilita el manejo declarativo de transacciones con @Transactional.
@Repository
Capa de persistencia. Spring activa la traducción automática de excepciones de infraestructura a DataAccessException. Úsalo en DAOs y repositorios JPA.
@Controller
Capa web. Indica que la clase maneja peticiones HTTP vía Spring MVC. @RestController = @Controller + @ResponseBody para APIs JSON/XML.
@Component("miUtilidad") // nombre explícito del bean
public class FechaUtility {{ '{' }} ... {{ '}' }}
@Service
public class PedidoService {{ '{' }}
  @Transactional
  public void crearPedido(Pedido p) {{ '{' }} ... {{ '}' }}
{{ '}' }}
@Repository
public class PedidoRepository {{ '{' }} ... {{ '}' }}
@RestController
@RequestMapping("/pedidos")
public class PedidoController {{ '{' }} ... {{ '}' }}
Sin estereotipos (manual)
@Bean en @Configuration para cada clase
Configuración verbose y propensa a errores
Sin traducción de excepciones
Sin soporte AOP por capa
Con estereotipos (@ComponentScan)
Detección automática en el classpath
Semántica clara por capa
Traducción automática en @Repository
AOP por capa (transacciones, seguridad)
El nombre por defecto del bean es el nombre de la clase con la primera letra en minúscula. PedidoService → pedidoService. Puedes especificar un nombre con @Service("nombre").
09Módulo 2

@Autowired & Dependency Injection

@Autowired instruye a Spring para que resuelva e inyecte la dependencia por tipo. Existen tres modalidades de inyección: campo, setter y constructor.

Inyección por Campo
La más concisa pero la más problemática: no permite inmutabilidad, dificulta las pruebas unitarias sin contenedor Spring y oculta dependencias. Evitar en código de producción.
Inyección por Setter
Permite dependencias opcionales (required=false) y reasignación. Útil para dependencias circulares en casos excepcionales. El bean puede existir sin la dependencia.
Inyección por Constructor
La forma recomendada. Garantiza inmutabilidad, facilita tests unitarios (sin Spring), hace explícitas las dependencias obligatorias y evita dependencias circulares en arranque.
@Qualifier & @Primary
@Primary marca el bean preferido cuando hay varios del mismo tipo. @Qualifier("nombre") selecciona un bean específico por nombre. @Qualifier tiene mayor precedencia.
// Campo (evitar)
@Autowired
private PedidoService pedidoService;
// Setter (dependencias opcionales)
@Autowired(required = false)
public void setCache(CacheService cache) {{ '{' }}
  this.cache = cache;
{{ '}' }}
// Constructor (recomendado)
public OrderController(PedidoService pedidoService,
                       @Qualifier("emailNotifier") Notifier notifier) {{ '{' }}
  this.pedidoService = pedidoService;
  this.notifier = notifier;
{{ '}' }}
Dependencia Circular (problema)
ClassA → ClassB → ClassA
Con constructor injection:
BeanCurrentlyInCreationException
al arrancar la app
Soluciones
1. Refactorizar (solución ideal)
2. @Lazy en uno de los constructores
3. Setter injection en uno de los beans
4. Extraer la dependencia común a un tercero
Si solo hay un constructor, @Autowired es opcional desde Spring 4.3. Spring lo detecta automáticamente. Con Lombok @RequiredArgsConstructor no necesitas escribirlo.
10Módulo 2

Constructor Injection

La inyección por constructor es la práctica recomendada por el equipo de Spring. Garantiza que el bean esté en un estado válido e inmutable desde el momento de su creación.

Inmutabilidad
Las dependencias pueden declararse final. Una vez construido el bean, sus dependencias no pueden cambiar. Esto elimina toda una clase de bugs en aplicaciones concurrentes.
Testabilidad
Para un test unitario, simplemente creas la instancia con new MiServicio(mockDep). No necesitas Spring, Mockito con @InjectMocks, ni reflexión para inyectar los mocks.
Dependencias Explícitas
La firma del constructor documenta exactamente qué necesita el bean. Si el constructor tiene demasiados parámetros, es una señal de que la clase viola el principio de responsabilidad única.
Lombok @RequiredArgsConstructor
Genera automáticamente un constructor con todos los campos final o @NonNull. Elimina el boilerplate manteniendo todos los beneficios de la inyección por constructor.
// Sin Lombok (verboso)
@Service
public class FacturaService {{ '{' }}
  private final ClienteRepository clienteRepo;
  private final ProductoRepository productoRepo;
  private final NotificationService notifier;
  public FacturaService(ClienteRepository clienteRepo,
                       ProductoRepository productoRepo,
                       NotificationService notifier) {{ '{' }}
    this.clienteRepo = clienteRepo;
    this.productoRepo = productoRepo;
    this.notifier = notifier;
  {{ '}' }}
{{ '}' }}
// Con Lombok (equivalente)
@Service
@RequiredArgsConstructor
public class FacturaService {{ '{' }}
  private final ClienteRepository clienteRepo;
  private final ProductoRepository productoRepo;
  private final NotificationService notifier;
{{ '}' }}
Un test unitario limpio: new FacturaService(new FakeClienteRepo(), new FakeProductoRepo(), new FakeNotifier()). Sin Spring, sin reflexión, sin magic.
11Módulo 2

Bean Scopes

El scope de un bean determina cuántas instancias crea Spring y cuánto tiempo viven. Spring Boot ofrece cinco scopes: dos genéricos y tres específicos para aplicaciones web.

1️⃣
Singleton (por defecto)
Una sola instancia por contexto de aplicación. Creada al arrancar, compartida por todos los consumidores, destruida al cerrar el contexto. Cuidado con el estado mutable.
Prototype
Nueva instancia en cada solicitud de bean al contenedor. Spring no gestiona el ciclo de vida completo: no llama a @PreDestroy. Úsalo para objetos con estado.
Request
Una instancia por petición HTTP. Creada al recibir la request, destruida al enviar la response. Disponible solo en contextos web (WebApplicationContext).
Session
Una instancia por sesión HTTP. Vive mientras dura la sesión del usuario. Ideal para mantener estado de usuario entre peticiones (carrito de compras, preferencias).
Application
Una instancia por ServletContext. Similar a singleton pero scoped al ciclo de vida del servlet. Compartido entre todos los usuarios de la aplicación web.
Scoped Proxy
Inyectar un bean de scope corto (request) en uno de scope largo (singleton) requiere un proxy: @Scope(value="request", proxyMode=ScopedProxyMode.TARGET_CLASS).
// Singleton (defecto)
@Service
public class ConfigService {{ '{' }} ... {{ '}' }}
// Prototype
@Component
@Scope("prototype")
public class ReportBuilder {{ '{' }} ... {{ '}' }}
// Request con proxy
@Component
@Scope(value = "request",
      proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContext {{ '{' }} ... {{ '}' }}
Un bean singleton con estado mutable compartido entre hilos es un problema de concurrencia. Usa ThreadLocal, @Scope("prototype") o @Scope("request") según el caso.
12Módulo 2

@Profile & @Configuration

@Configuration define clases de configuración Java para declarar beans. @Profile y @Conditional permiten activar beans según el entorno o condiciones programáticas.

@Configuration
Clase que actúa como fuente de definiciones de beans. Spring genera un proxy CGLIB de la clase para interceptar llamadas @Bean y garantizar la semántica singleton.
@Profile
Activa un bean o clase de configuración solo cuando el perfil indicado está activo. Se activa con spring.profiles.active=prod en application.properties o como argumento JVM.
@Conditional
Condición programática genérica. Implementa la interfaz Condition con el método matches(). Base de todas las anotaciones @ConditionalOn* de Spring Boot.
SpEL en @Value
Spring Expression Language permite expresiones dinámicas: @Value("#{{ '{' }}systemProperties['user.home']{{ '}' }}"), operaciones matemáticas, acceso a otros beans y condicionales ternarios.
@Configuration
public class DataSourceConfig {{ '{' }}
  @Bean
  @Profile("dev")
  public DataSource h2DataSource() {{ '{' }}
    return new EmbeddedDatabaseBuilder()
      .setType(EmbeddedDatabaseType.H2).build();
  {{ '}' }}
  @Bean
  @Profile("prod")
  public DataSource pgDataSource(@Value("${{ '{' }}db.url{{ '}' }}") String url) {{ '{' }}
    return DataSourceBuilder.create().url(url).build();
  {{ '}' }}
{{ '}' }}
// @Conditional personalizado
public class OnLinuxCondition implements Condition {{ '{' }}
  public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata m) {{ '{' }}
    return System.getProperty("os.name").contains("Linux");
  {{ '}' }}
{{ '}' }}
@Bean
@Conditional(OnLinuxCondition.class)
public LinuxFileWatcher fileWatcher() {{ '{' }} ... {{ '}' }}
// SpEL en @Value
@Value("#{{ '{' }}T(java.lang.Math).random() * 100{{ '}' }}")
private double randomValue;
@Value("#{{ '{' }}configBean.timeout > 30 ? 'alto' : 'bajo'{{ '}' }}")
private String nivelTimeout;
1
Activa el perfil en application.properties: spring.profiles.active=prod.
2
O como argumento JVM: -Dspring.profiles.active=prod.
3
O con variable de entorno: SPRING_PROFILES_ACTIVE=prod.
4
Usa @Profile("!prod") para activar en cualquier perfil excepto producción.
5
Combina perfiles: @Profile("{{ '{' }}"prod", "staging"{{ '}' }}") o @Profile("prod & cloud").
@Import(OtraConfigClass.class) importa definiciones de beans de otra clase @Configuration sin necesidad de estar en el package base del @ComponentScan.

¿Para qué sirve ObjectProvider<T> en la inyección de dependencias?
A
Es equivalente a Optional<T> de Java y solo gestiona nullability
B
Permite inyección lazy, dependencias opcionales, y obtener múltiples instancias de beans prototype de forma segura sin acoplar al ApplicationContext
C
Solo sirve para inyectar beans de scope request en beans singleton
D
Es una forma de crear beans sin registrarlos en el contexto Spring
✓ ObjectProvider<T> ofrece: getIfAvailable() (null si no existe), getIfUnique() (null si hay varios), stream() para todos los beans, e ifAvailable(consumer) para lógica condicional. Ideal para dependencias opcionales.
✗ ObjectProvider<T> es una alternativa elegante a inyectar ApplicationContext. Ofrece getObject() (lanza si no existe), getIfAvailable() (null-safe), stream() para múltiples instancias, y resolución lazy.

¿Qué son las interfaces Aware en Spring y para qué sirven?
A
Son interfaces para marcar beans que requieren inyección obligatoria
B
Permiten que un bean reciba referencias a infraestructura del contenedor (ApplicationContext, BeanFactory, Environment) a través de callbacks de inyección
C
Son interfaces para implementar validaciones automáticas al crear beans
D
Solo las usa Spring internamente; los desarrolladores no pueden implementarlas
✓ Ejemplos: ApplicationContextAware (recibe el contexto), BeanNameAware (recibe el nombre del bean), EnvironmentAware (recibe el Environment). Mejor alternativa: inyectar directamente vía constructor para evitar acoplamiento a Spring.
✗ Implementando ApplicationContextAware, Spring llama a setApplicationContext() después de crear el bean. Útil pero acopla al framework. Prefiere inyección directa por constructor cuando sea posible.
