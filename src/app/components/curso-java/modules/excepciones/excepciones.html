29Excepciones

try / catch / finally

Las excepciones son eventos anormales que interrumpen el flujo normal del programa. Java usa un mecanismo estructurado que separa el código normal del de manejo de errores.

Tipos de Throwable

Checked Exception
Hereda de Exception (no de RuntimeException). El compilador obliga a manejarlas con try-catch o declararlas con throws. Ej: IOException, SQLException.
Unchecked Exception
Hereda de RuntimeException. El compilador no obliga a capturarlas. Indican errores de programación. Ej: NullPointerException, ArrayIndexOutOfBoundsException, ClassCastException.
Error
Hereda de Error. Condiciones graves del sistema que normalmente no deben capturarse. Ej: OutOfMemoryError, StackOverflowError. No representan bugs del programa.

Anatomía del bloque try-catch-finally

Estructura completa — reglas del examen Oracle
try {{ '{' }}
  // 1. Código que puede lanzar excepción
  int resultado = dividir(10, 0);
{{ '}' }} catch (ArithmeticException e) {{ '{' }}
  // 2. Captura más específica PRIMERO
  System.out.println("Aritmética: " + e.getMessage());
{{ '}' }} catch (RuntimeException e) {{ '{' }}
  // 3. Más general después
  System.out.println("Runtime: " + e.getMessage());
{{ '}' }} catch (IOException | SQLException e) {{ '{' }}
  // 4. Multi-catch (Java 7+) — variable efectivamente final
  System.out.println("I/O o BD: " + e.getMessage());
{{ '}' }} finally {{ '{' }}
  // 5. Siempre se ejecuta (incluso con return en try)
  System.out.println("Limpieza garantizada");
{{ '}' }}
Reglas de oro para el examen: (1) Los catch más específicos van primero — el compilador rechaza un catch de clase padre antes que el de la hija. (2) En multi-catch la variable e es implícitamente final — no puedes reasignarla. (3) finally se ejecuta siempre, incluso con return en el try. La única excepción es System.exit() o un crash de JVM.

// Método DEBE declarar throws o envolver en try-catch

Reglas de orden de bloques catch

Error de compilación — padre antes que hija
try {{ '{' }} ... {{ '}' }}
catch (Exception e) {{ '{' }} ... {{ '}' }}     // PADRE
catch (ArithmeticException e) {{ '{' }} ... {{ '}' }}
// ↑ COMPILE ERROR: already caught by Exception
Correcto — específico antes que general
try {{ '{' }} ... {{ '}' }}
catch (ArithmeticException e) {{ '{' }} ... {{ '}' }}// HIJA
catch (RuntimeException e) {{ '{' }} ... {{ '}' }}  // PADRE
catch (Exception e) {{ '{' }} ... {{ '}' }}        // ABUELO
Para el examen: (1) Si en multi-catch pones dos tipos donde uno hereda del otro, es error de compilación: catch(Exception | ArithmeticException e) es ilegal. (2) catch(Exception) captura cualquier Exception pero NO captura Error — son ramas independientes de Throwable. (3) Solo catch(Throwable) captura todo, pero es mala práctica.

Excepciones Personalizadas

Las excepciones propias (custom exceptions) modelan errores del dominio de negocio con mensajes significativos, datos adicionales y una jerarquía coherente. Son esenciales en aplicaciones de producción.

¿Cuándo crear checked vs unchecked?

Checked custom — extiende Exception
public class DatosInvalidosException
    extends Exception {{ '{' }}

  public DatosInvalidosException(String msg) {{ '{' }}
    super(msg);
  {{ '}' }}
  // El llamador DEBE capturarla o propagarla
{{ '}' }}
Unchecked custom — extiende RuntimeException
public class SaldoInsuficienteException
    extends RuntimeException {{ '{' }}

  private final double saldo, monto;

  public SaldoInsuficienteException(double s, double m) {{ '{' }}
    super(String.format("Saldo %.2f insuficiente para retirar %.2f", s, m));
    this.saldo = s; this.monto = m;
  {{ '}' }}
  public double getSaldo() {{ '{' }} return saldo; {{ '}' }}
{{ '}' }}
Guía de diseño: Usa checked cuando el llamador puede razonablemente recuperarse (ej: archivo no encontrado → buscar alternativa). Usa unchecked para errores de programación o condiciones que no deberían ocurrir en código correcto (ej: argumento nulo, estado inválido). La tendencia moderna favorece unchecked para no contaminar las firmas de métodos.

Los 4 constructores estándar (best practice OCP)

Plantilla completa de excepción personalizada
public class MiExcepcion extends RuntimeException {{ '{' }}

  // 1. Sin argumentos
  public MiExcepcion() {{ '{' }} super(); {{ '}' }}

  // 2. Con mensaje
  public MiExcepcion(String mensaje) {{ '{' }} super(mensaje); {{ '}' }}

  // 3. Con causa (encadenamiento de excepciones)
  public MiExcepcion(Throwable causa) {{ '{' }} super(causa); {{ '}' }}

  // 4. Mensaje + causa — el más completo
  public MiExcepcion(String msg, Throwable causa) {{ '{' }}
    super(msg, causa);
  {{ '}' }}
{{ '}' }}

Métodos de diagnóstico en producción

getMessage()
Retorna el mensaje pasado al constructor. Útil para logs de negocio: e.getMessage() → "Saldo 50.00 insuficiente"
getCause()
Retorna la excepción original encadenada o null. Permite ver la causa raíz: e.getCause().getMessage()
printStackTrace()
Imprime la traza completa de llamadas en stderr. En producción usa un logger: logger.error("Error", e)
toString()
Retorna clase + mensaje: "com.app.MiExcepcion: Saldo insuficiente". Es lo que se imprime automáticamente con System.out.println(e)
32Excepciones

try-with-resources y AutoCloseable

try-with-resources (Java 7+) cierra automáticamente cualquier recurso que implemente AutoCloseable al finalizar el bloque, incluso si ocurre una excepción. Elimina el patrón verboso de finally manual.

Antes de Java 7 vs try-with-resources

Java 6 — finally manual (propenso a bugs)
Connection conn = null;
try {{ '{' }}
  conn = getConnection();
  conn.doWork();
{{ '}' }} catch (SQLException e) {{ '{' }}
  log(e);
{{ '}' }} finally {{ '{' }}
  if (conn != null) {{ '{' }}
    try {{ '{' }} conn.close(); {{ '}' }}
    catch (SQLException e2) {{ '{' }} log(e2); {{ '}' }}
  {{ '}' }}
{{ '}' }} // ← 15+ líneas para algo simple
Java 7+ — try-with-resources
try (Connection conn = getConnection()) {{ '{' }}
  conn.doWork();
{{ '}' }} catch (SQLException e) {{ '{' }}
  log(e);
{{ '}' }}
// conn.close() llamado automáticamente
// ← 6 líneas, mismo comportamiento

Múltiples recursos — orden de cierre (LIFO)

Los recursos se cierran en orden INVERSO al de apertura
try (
  InputStream in = new FileInputStream("data.bin");  // abre 1ro
  BufferedReader br = new BufferedReader(
                   new InputStreamReader(in)) // abre 2do
) {{ '{' }}
  String line;
  while ((line = br.readLine()) != null)
    System.out.println(line);
{{ '}' }}
// Cierre automático: br.close() → in.close() (LIFO)

Excepciones suprimidas (Suppressed Exceptions)

Cuando tanto el body como el close() lanzan excepción
class RecursoFallido implements AutoCloseable {{ '{' }}
  public void close() throws Exception {{ '{' }}
    throw new Exception("Error en close()");
  {{ '}' }}
{{ '}' }}

try (RecursoFallido r = new RecursoFallido()) {{ '{' }}
  throw new Exception("Error en body");  // ← principal
{{ '}' }} catch (Exception e) {{ '{' }}
  System.out.println(e.getMessage());
  // → "Error en body" (la del body es la principal)
  Throwable[] sup = e.getSuppressed();
  System.out.println(sup[0].getMessage());
  // → "Error en close()" (suprimida, no perdida)
{{ '}' }}

Java 9+: variables efectivamente finales en try()

Java 9 — reutilizar recurso ya declarado (effectively final)
BufferedReader reader = new BufferedReader(...);
// Java 9+: usar variable ya declarada si es efectivamente final
try (reader) {{ '{' }}  // ← no redeclara el tipo
  System.out.println(reader.readLine());
{{ '}' }}
// reader.close() se llama automáticamente
// Java 7-8: debías redeclarar: try(BufferedReader r = reader)

Implementar AutoCloseable personalizado

Recurso propio compatible con try-with-resources
class Conexion implements AutoCloseable {{ '{' }}
  private String nombre;
  Conexion(String n) {{ '{' }}
    nombre = n;
    System.out.println("Abriendo: " + nombre);
  {{ '}' }}
  public void close() {{ '{' }}  // puede throws Exception
    System.out.println("Cerrando: " + nombre);
  {{ '}' }}
{{ '}' }}

try (Conexion c = new Conexion("BD-1")) {{ '{' }}
  System.out.println("Trabajando...");
{{ '}' }}
// → Abriendo: BD-1 → Trabajando... → Cerrando: BD-1
Para el examen: (1) AutoCloseable.close() puede declarar cualquier excepción checked. Closeable.close() solo puede lanzar IOException. (2) Los recursos se cierran en orden inverso al de declaración (LIFO). (3) Si el body y el close() lanzan, la del body es la principal y la del close() es suprimida — accesible con getSuppressed(), no se pierde.
