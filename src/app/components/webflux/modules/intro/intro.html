01Módulo 1 · Programación Reactiva

¿Qué es la Programación Reactiva?

Un paradigma orientado a flujos de datos asíncronos y propagación de cambios, diseñado para sistemas altamente concurrentes.

Reactive Manifesto
Responsive (responde a tiempo), Resilient (falla con gracia), Elastic (escala bajo carga), Message-Driven (comunicación asíncrona).
Problema del blocking
Thread-per-request: cada petición bloquea un hilo esperando I/O. Con 1000 conexiones simultáneas, necesitas 1000 hilos → alta memoria y context-switching.
Event Loop
Un hilo gestiona miles de conexiones usando callbacks. Cuando el I/O completa, el callback se ejecuta. Netty usa este modelo. Ningún hilo queda bloqueado esperando.
Push vs Pull
Imperativo: el código solicita datos (pull). Reactivo: los datos fluyen cuando están disponibles (push). El consumidor controla el ritmo mediante backpressure.
Blocking (Spring MVC)
Thread bloqueado esperando DB 1000 req → 1000 threads Alto uso de memoria Context switching costoso
Non-Blocking (WebFlux)
Thread libre mientras espera DB 1000 req → pocos threads Bajo uso de memoria Netty event loop eficiente
Reactivo NO significa más rápido para una sola petición — significa mejor uso de recursos con miles de peticiones concurrentes.

Reactive Streams Specification

Estándar de la industria (Java 9 java.util.concurrent.Flow) para streams reactivos interoperables.

Publisher
subscribe(Subscriber) — fuente de datos. Implementaciones: Reactor Mono/Flux, RxJava Observable, JDK SubmissionPublisher.
Subscriber
onSubscribe(s), onNext(t), onError(t), onComplete(). Llama s.request(n) en onSubscribe para solicitar datos.
Subscription
request(n) para pedir N elementos. cancel() para detener el flujo. Es el mecanismo de backpressure — el consumer controla el ritmo.
Processor

03Módulo 1 · Programación Reactiva

Project Reactor

Implementación de Reactive Streams de Pivotal, base de Spring WebFlux. Dos tipos fundamentales: Mono y Flux.

1️⃣
Mono<T>
Emite 0 o 1 elemento y completa (o falla). Equivalente a CompletableFuture pero reactivo. Ideal para operaciones que retornan un único resultado o vacío.
Flux<T>
Emite 0 a N elementos, luego completa o falla. Para streams de múltiples elementos. Soporta backpressure completo mediante Reactive Streams spec.
Cold Publisher
No emite nada hasta que hay un suscriptor. Cada suscriptor recibe el flujo completo desde el inicio. Mono.just() y Flux.fromIterable() son cold.
Dependencia Maven
spring-boot-starter-webflux incluye reactor-core, Netty y Spring WebFlux. Sin servlet container — Netty como servidor por defecto.
// Mono: 0 o 1 elemento
Mono<String> mono = Mono.just("Hola");
Mono<String> empty = Mono.empty();
Mono<String> lazy = Mono.defer(() -> Mono.just(calcular()));
// Flux: 0-N elementos
Flux<Integer> nums = Flux.range(1, 10);
Flux<String> items = Flux.fromIterable(lista);
// Suscripción (necesaria para que emita!)
mono.subscribe(v -> log(v), err -> err.printStackTrace());
Sin suscriptor, nada ocurre. Mono y Flux son declaraciones de qué hacer cuando se suscriba — el operador subscribe() desencadena la ejecución.
04Módulo 1 · Programación Reactiva

Backpressure

Mecanismo por el cual un suscriptor controla el ritmo al que recibe datos, evitando ser sobrepasado.

request(n)
El Subscriber llama subscription.request(n) para pedir exactamente N elementos. El Publisher no enviará más que los solicitados.
BUFFER
Almacena elementos que llegan más rápido de lo que se consumen. Por defecto tiene límite — cuando se llena lanza OverflowException.
DROP
Descarta elementos cuando el downstream no puede consumirlos. Útil para streams de tiempo real donde los datos viejos no importan (p.ej. telemetría).
LATEST
Conserva sólo el último elemento emitido mientras el downstream no está listo. DROP pero con el elemento más reciente disponible cuando el consumer esté libre.
Flux.range(1, 1000)
  .onBackpressureBuffer(100)  // buffer hasta 100
  // .onBackpressureDrop() // descarta extras
  // .onBackpressureLatest() // solo el último
  .publishOn(Schedulers.boundedElastic())
  .subscribe(i -> procesarLento(i));
En WebFlux, el backpressure se propaga automáticamente desde el cliente HTTP hasta la fuente de datos. No necesitas gestionarlo manualmente en la mayoría de casos.

Cold vs Hot Publishers

La diferencia entre publishers que comienzan cuando llega un suscriptor (cold) y los que emiten independientemente (hot).

Cold Publisher
Cada suscriptor recibe todos los datos desde el principio. Ejemplo: Flux.fromIterable(), peticiones HTTP, DB queries. Suscriptor tarda → datos esperan.
Hot Publisher
Emite independientemente. Los suscriptores tardíos pierden datos previos. Ejemplo: eventos UI, WebSocket, Sinks.Many multicast.
ConnectableFlux
flux.publish() crea ConnectableFlux. Todos los suscriptores se registran, luego .connect() inicia la emisión para todos simultáneamente.
share() / autoConnect()
share() = publish().refCount(): empieza cuando hay ≥1 suscriptor, para cuando llega a 0. autoConnect(n): empieza cuando hay n suscriptores.
Sinks
API programática para hot publishers. Sinks.many().multicast().onBackpressureBuffer() para emitir eventos desde código imperativo a flujos reactivos.
Caso de uso real
SSE (Server-Sent Events) con WebFlux: una Sink emite eventos del negocio, múltiples clientes HTTP se suscriben al flujo hot y reciben los eventos en tiempo real.
06Módulo 1 · Programación Reactiva

Schedulers

Controla en qué thread se ejecuta cada parte del pipeline reactivo.

Schedulers.parallel()
Pool de threads = número de CPUs. Para operaciones CPU-intensivas NO bloqueantes. NO usar para I/O bloqueante — bloquearía el pool.
Schedulers.boundedElastic()
Pool elástico acotado (max 10 * CPUs). Para llamadas bloqueantes (JDBC, servicios legados). Puede crecer bajo carga pero tiene límite superior.
1️⃣
Schedulers.single()
Un único thread reutilizable. Para operaciones que deben ser serializadas (acceso exclusivo a recurso). Similar a un "single-threaded executor".
publishOn vs subscribeOn
publishOn: cambia el scheduler de los operadores AGUAS ABAJO. subscribeOn: cambia el scheduler de la FUENTE (el primero definido gana).
Flux.fromIterable(ids)
  .subscribeOn(Schedulers.boundedElastic())  // fuente en elastic
  .map(id -> callBlockingDb(id))  // también en elastic
  .publishOn(Schedulers.parallel())  // cambia a parallel
  .map(dto -> transform(dto))  // ejecuta en parallel
  .subscribe();
El mayor error en WebFlux: llamar código bloqueante (Thread.sleep, JDBC, RestTemplate) en Schedulers.parallel(). Usa siempre boundedElastic para operaciones blocking.
07Módulo 1 · Programación Reactiva

Operadores de Composición

Combina y transforma flujos reactivos de forma declarativa con los operadores más importantes.

flatMap
Transformación async concurrente. Para cada elemento, crea un inner publisher. Los resultados se intercalan (no garantiza orden). Máxima concurrencia controlable.
concatMap
Como flatMap pero secuencial — espera a que el inner publisher complete antes de procesar el siguiente. Garantiza orden. Menor throughput que flatMap.
switchMap
Cancela el inner publisher anterior cuando llega un nuevo elemento. Útil para "tomar solo el último" (p.ej. búsquedas en tiempo real con debounce).
zip / merge
zip: combina elementos sincronizados (par a par, se detiene en el más corto). merge: suscribe a todos concurrentemente, emite según llegan.
// flatMap: concurrente, sin orden garantizado
Flux.range(1,5).flatMap(id -> repo.findById(id))
// concatMap: secuencial, orden garantizado
Flux.range(1,5).concatMap(id -> repo.findById(id))
// zip: combina par a par
Mono.zip(getUser(id), getOrders(id))
  .map(tuple -> new UserDTO(tuple.getT1(), tuple.getT2()))
