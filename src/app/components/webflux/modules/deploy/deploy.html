Modelo de Hilos de Netty

Cómo funciona el event loop de Netty — la razón por la que WebFlux necesita menos threads.

Event Loop Groups
Netty tiene dos grupos: Boss group — acepta conexiones entrantes (1 thread). Worker group — procesa I/O y lógica (por defecto: 2×núcleos CPU). Un NioEventLoop por thread.
NioEventLoop
Cada NioEventLoop ejecuta un selector NIO que monitoriza múltiples canales. Un solo thread maneja miles de conexiones concurrentes sin bloquearse. No confundir "concurrente" con "paralelo".
Thread count por defecto
Runtime.getRuntime().availableProcessors() × 2. En una máquina con 4 CPU → 8 worker threads. Mucho menos que el pool de 200 threads de Tomcat.
No blocking en event loop
Regla fundamental: nunca bloquees en el event loop de Netty. Thread.sleep(), JDBC, files I/O bloqueante → pausa toda la cadena. Usa Schedulers.boundedElastic() para operaciones bloqueantes.

BlockHound

Detección en tests y desarrollo de código bloqueante ejecutado en threads reactivos.

¿Qué es BlockHound?
Agente Java que intercepta llamadas bloqueantes (Thread.sleep, I/O bloqueante, JDBC) cuando se ejecutan en threads marcados como non-blocking (event loops de Netty, parallel scheduler).
BlockHound.install()
Debe llamarse al inicio de la JVM — antes de que cualquier class loader cargue clases bloqueantes. En Spring Boot: en el main() antes de SpringApplication.run() o en un @BeforeAll de test.
@NonBlocking
Anotación de Reactor para marcar threads como non-blocking. Los event loops de Netty ya están marcados. BlockHound lanza BlockingOperationException si detecta código bloqueante en un thread así marcado.
Allowlist personalizada
Para permitir operaciones específicas: BlockHound.install(b -> b.allowBlockingCallsInside("ClassName", "methodName")). Úsalo solo cuando sea absolutamente necesario.

Docker y Kubernetes para WebFlux

Containerización optimizada para aplicaciones reactivas con Netty.

Dockerfile multi-stage
WebFlux con Netty no necesita servlet container (no Tomcat). El JAR incluye Netty embebido. Multi-stage: build con Maven/Gradle, runtime con JRE slim o distroless.
Memoria reducida
WebFlux usa significativamente menos memoria que Spring MVC bajo carga: menos threads = menos stack memory. Typical: 256–512 MB vs 512 MB–1 GB para Spring MVC equivalente.
Kubernetes probes
Spring Actuator con WebFlux expone endpoints reactivos. /actuator/health/liveness — el pod puede recibir tráfico. /actuator/health/readiness — la app está lista. Configura en K8s livenessProbe y readinessProbe.
Escalado horizontal
WebFlux es stateless (si evitas estado en memoria) → escala horizontalmente sin coordinación. HPA (Horizontal Pod Autoscaler) basado en métricas de CPU/memoria o métricas custom de Micrometer.
# Dockerfile multi-stage para WebFlux
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY . .
RUN ./mvnw package -DskipTests
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
# Flags JVM para contenedores
ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0"
EXPOSE 8080
ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]
