08Módulo 2 · Flux & Mono

Creación de Mono

Todas las formas de instanciar un Mono, desde valores estáticos hasta fuentes asíncronas y lazy.

Mono.just / empty / error
just(T) — eager, evalúa inmediatamente. empty() — completa sin emitir. error(Throwable) — señal onError inmediata.
Mono.fromCallable
Wrappea una llamada bloqueante. Se evalúa en la suscripción. Úsalo con subscribeOn(Schedulers.boundedElastic()) para no bloquear el event loop.
Mono.fromFuture
Convierte un CompletableFuture en Mono reactivo. El Future ya debe estar en ejecución. Soporta cancelación mediante la propagación de cancel().
Mono.defer
Lazy — el supplier se ejecuta en cada suscripción. Captura el estado actual del entorno (timestamp, variables locales). Imprescindible para retry correcto.
Mono.just("eager")                   // valor capturado YA
Mono.fromCallable(() -> db.findById(1)) // lazy, blocking OK
Mono.fromSupplier(this::calcular)        // lazy, no checked ex
Mono.fromFuture(asyncService.call())    // CompletableFuture
Mono.defer(() -> Mono.just(ahora()))   // tiempo capturado tarde
// subscribe con consumer / error / complete
mono.subscribe(
  val -> process(val),
  err -> handle(err),
  () -> complete()
);
09Módulo 2 · Flux & Mono

Creación de Flux

Fábricas estáticas y fuentes programáticas para crear streams de múltiples elementos.

Flux estáticos
just(a,b,c), range(1,10), fromIterable(list), fromArray(arr), fromStream(stream). Todos cold, evalúan en suscripción.
Flux.interval
Emite Long crecientes a intervalos fijos. Hot, emite en Schedulers.parallel(). Requiere backpressure — el consumer debe ser tan rápido como el interval.
Flux.generate
Programático síncrono. El BiFunction recibe estado + SynchronousSink. Solo se puede llamar next() UNA VEZ por iteración. Ideal para generadores con estado.
Flux.create
Programático asíncrono. Recibe FluxSink que puede llamarse desde múltiples threads. Permite bridge desde APIs callback/event-listener. Especifica estrategia overflow.
// generate: estado incrementa
Flux.generate(() -> 0, (estado, sink) -> {{ '{' }}
  sink.next(estado);
  if (estado >= 9) sink.complete();
  return estado + 1;
{{ '}' }})
// create: bridge con listener
Flux.create(sink -> {{ '{' }}
  eventBus.on("data", evt -> sink.next(evt));
  eventBus.on("done", () -> sink.complete());
{{ '}' }}, OverflowStrategy.BUFFER)
10Módulo 2 · Flux & Mono

map, flatMap, concatMap, switchMap

Los operadores de transformación más importantes — cada uno con diferente semántica de concurrencia y orden.

map
Transformación síncrona 1:1. Cada elemento entra, un elemento sale. No puede retornar un Publisher. Siempre preserva el orden.
flatMap
Async, concurrente. Cada elemento → Publisher interno. Suscribe a todos concurrentemente. Los resultados se intercalan según lleguen (sin orden garantizado).
concatMap
Async, secuencial. Suscribe al siguiente inner publisher SOLO cuando el anterior completa. Orden garantizado. Menor throughput que flatMap pero predecible.
flatMapSequential
Como flatMap (concurrente) pero los resultados se emiten en el orden original. Internamente usa un buffer. Combina el throughput de flatMap con el orden de concatMap.
flatMap (sin orden)
Entrada: [1, 2, 3] Llama API concurrente Salida posible: [2, 1, 3] Máximo throughput
concatMap (con orden)
Entrada: [1, 2, 3] Llama API secuencial Salida garantizada: [1, 2, 3] Menor throughput
Regla práctica: usa flatMap cuando el orden no importa (más rápido); usa concatMap cuando necesitas preservar el orden de la fuente.
11Módulo 2 · Flux & Mono

filter, take & skip

Operadores de filtrado y selección para controlar qué elementos pasan por el pipeline.

filter / distinct
filter(pred) — pasa elementos que cumplen predicado. distinct() — elimina duplicados (usa hashCode/equals). distinctUntilChanged() — elimina repetidos consecutivos.
take
take(n) — primeros N elementos luego cancela upstream. takeLast(n) — últimos N (requiere buffer). takeUntil(pred) — hasta que se cumple el predicado.
skip
skip(n) — omite los primeros N. skipLast(n) — omite los últimos N. skipUntil(pred) — omite hasta que el predicado es true.
elementAt / first / last
elementAt(i) — Mono con el elemento en la posición i. next() — primer elemento como Mono. last() — último elemento como Mono.
Flux.range(1, 20)
  .filter(n -> n % 2 == 0)      // solo pares: 2,4,6...
  .skip(2)                     // omite 2,4 → 6,8...
  .take(3)                     // toma solo 6,8,10
  .subscribe(System.out::println);
12Módulo 2 · Flux & Mono

zip, merge & concat

Combinación de múltiples publishers para orquestar operaciones paralelas o secuenciales.

zip
Combina pares de elementos sincronizados. Espera un elemento de CADA fuente, los empaqueta en Tuple. Se detiene cuando la fuente más corta completa.
merge
Suscribe a todos los publishers concurrentemente. Los elementos se intercalan según llegan. El stream completa cuando todos completan. Usa mergeWith() para 2.
concat
Secuencial — suscribe al segundo solo cuando el primero completa. Orden garantizado. Usa concatWith() para 2 publishers. Similar a flatMap con concurrency=1.
combineLatest
Emite cada vez que cualquier fuente emite, combinando con el último valor de las demás. Requiere que todas hayan emitido al menos una vez. Útil para formularios reactivos.
// zip: peticiones paralelas combinadas
Mono.zip(userService.find(id), orderService.find(id))
  .map(t -> new UserOrderDTO(t.getT1(), t.getT2()))
// merge: varios streams en uno
Flux.merge(emailFlux, pushFlux, smsFlux)
  .subscribe(notif -> send(notif));
// concat: página 1, luego página 2
Flux.concat(getPage(1), getPage(2), getPage(3))
13Módulo 2 · Flux & Mono

Manejo de Errores

Estrategias para capturar, transformar y recuperarse de errores en pipelines reactivos.

onErrorReturn
Fallback a un valor estático cuando ocurre error. El stream completa normalmente con ese valor. No re-suscribe a la fuente. Simple pero limitado.
onErrorResume
Fallback a otro Publisher. Permite lógica compleja de recuperación (llamar API alternativa, retornar caché). El tipo de retorno debe ser compatible.
retry / retryWhen
retry(n) — re-suscribe N veces. retryWhen(Retry.backoff(3, Duration.ofSeconds(1))) — retry con exponential backoff. Esencial para llamadas a servicios externos.
timeout
Emite TimeoutException si no hay elementos en la duración especificada. Combina con onErrorResume para fallback en caso de timeout.
callExternalApi(id)
  .timeout(Duration.ofSeconds(3))
  .retryWhen(Retry.backoff(3, Duration.ofMillis(500)))
  .onErrorResume(TimeoutException.class,
    ex -> getCachedFallback(id))
  .onErrorMap(WebClientException.class,
    ex -> new ServiceUnavailableException(ex))
  .doOnError(e -> metrics.increment("errors"));
14Módulo 2 · Flux & Mono

Testing con StepVerifier

La herramienta estándar de Reactor para probar pipelines reactivos de forma síncrona y determinista.

// Verificar secuencia normal
StepVerifier.create(Flux.range(1,3))
  .expectNext(1, 2, 3)
  .verifyComplete();
// Verificar error
StepVerifier.create(Mono.error(new RuntimeException()))
  .expectErrorMatches(e -> e instanceof RuntimeException)
  .verify();
// withVirtualTime: simular tiempo
StepVerifier.withVirtualTime(() -> Flux.interval(Duration.ofHours(1)).take(3))
  .thenAwait(Duration.ofHours(3))
  .expectNextCount(3)
  .verifyComplete();
Métodos de expectativa
expectNext(T...), expectNextMatches(pred), expectNextCount(n), expectError(Class), expectErrorMessage(msg).
withVirtualTime
Simula tiempo sin esperar. El supplier debe crear el Publisher DENTRO de withVirtualTime. Luego usa thenAwait() para avanzar el reloj virtual.
Importante: siempre termina con verifyComplete(), verify(), o verifyError() — sin esta llamada, las expectativas no se verifican.
