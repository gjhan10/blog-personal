Singleton

Garantiza que una clase tenga una única instancia y proporciona un punto de acceso global.

Intención
Controlar la instanciación de una clase para que solo exista un objeto. El constructor es privado y el acceso se realiza a través de un método estático.
Cuándo usarlo
Cuando exactamente un objeto debe coordinar acciones: pool de conexiones, logger, registro de configuración, cache compartida.
Thread Safety
En Java moderno se prefiere el patrón "Initialization-on-demand holder" o un enum. El enum es thread-safe y resiste serialización.
Anti-patrón frecuente
Overuso del Singleton convierte el estado global en dependencia oculta, dificulta el testing (difícil de mockear) y crea acoplamiento alto.
// Forma recomendada en Java — Enum Singleton
public enum AppConfig {{ '{' }}
  INSTANCE;
  private final Properties props = new Properties();
  public String get(String key) {{ '{' }} return props.getProperty(key); {{ '}' }}
{{ '}' }}
// Uso
String val = AppConfig.INSTANCE.get("db.url");
// Alternativa: Initialization-on-demand holder
public class DatabasePool {{ '{' }}
  private static class Holder {{ '{' }}
    static final DatabasePool INSTANCE = new DatabasePool();
  {{ '}' }}
  public static DatabasePool getInstance() {{ '{' }} return Holder.INSTANCE; {{ '}' }}
{{ '}' }}

Factory Method

Define una interfaz para crear un objeto, pero deja que las subclases decidan qué clase instanciar.

Intención
El Creator declara el factory method abstracto que las subclases sobreescriben para crear productos concretos. El cliente trabaja con la interfaz Product.
Cuándo usarlo
Cuando no sabes de antemano la clase exacta del objeto a crear, o cuando quieres que las subclases especifiquen el objeto a crear sin alterar el código del cliente.
Participantes
Creator: declara el factory method. ConcreteCreator: lo implementa. Product: interfaz del producto. ConcreteProduct: implementación concreta.
vs Abstract Factory
Factory Method crea un producto via herencia. Abstract Factory crea familias de productos via composición. Factory Method es más simple y más común.
interface Dialog {{ '{' }}
  Button createButton(); // factory method
  default void render() {{ '{' }} createButton().render(); {{ '}' }}
{{ '}' }}
class WindowsDialog implements Dialog {{ '{' }}
  public Button createButton() {{ '{' }} return new WindowsButton(); {{ '}' }}
{{ '}' }}
class WebDialog implements Dialog {{ '{' }}
  public Button createButton() {{ '{' }} return new HtmlButton(); {{ '}' }}
{{ '}' }}

Abstract Factory

Proporciona una interfaz para crear familias de objetos relacionados sin especificar sus clases concretas.

Intención
Garantiza que los objetos producidos sean compatibles entre sí. Un cliente que usa WinFactory nunca mezcla botones Windows con checkboxes Mac.
Cuándo usarlo
Cuando el sistema debe ser independiente de cómo se crean sus productos, y necesitas garantizar que los productos de una familia se usen juntos.
Participantes
AbstractFactory: interfaz con métodos de creación. ConcreteFactory: crea una familia concreta. AbstractProduct: interfaz del producto. ConcreteProduct.
Extensibilidad
Añadir un nuevo tipo de producto rompe la interfaz AbstractFactory (OCP violado). Añadir una nueva familia (nueva plataforma) es fácil sin cambiar el cliente.
interface GUIFactory {{ '{' }}
  Button createButton();
  Checkbox createCheckbox();
{{ '}' }}
class WinFactory implements GUIFactory {{ '{' }}
  public Button createButton() {{ '{' }} return new WinButton(); {{ '}' }}
  public Checkbox createCheckbox() {{ '{' }} return new WinCheckbox(); {{ '}' }}
{{ '}' }}
class Application {{ '{' }}
  private final GUIFactory factory;
  Application(GUIFactory f) {{ '{' }} this.factory = f; {{ '}' }}
  void buildUI() {{ '{' }}
    Button b = factory.createButton(); // no sabe el tipo concreto
  {{ '}' }}
{{ '}' }}

Builder

Separa la construcción de un objeto complejo de su representación, permitiendo el mismo proceso construir distintas representaciones.

Intención
El Director coordina la construcción usando el Builder. El cliente puede usar el Director para construir variantes, u omitirlo y llamar al Builder directamente.
Cuándo usarlo
Objetos con muchos parámetros opcionales (evita constructores con 10 parámetros), múltiples representaciones del mismo proceso de construcción, construcción paso a paso.
Builder fluente en Java
En Java moderno, el Builder fluente (sin Director) es muy común: Pizza.builder().size(L).toppings(List.of(CHEESE)).build(). Lombok @Builder lo genera automáticamente.
vs Constructor/Telescoping
El anti-patrón "telescoping constructor" tiene N constructores sobreargados. Builder lo elimina y hace el código legible. Útil cuando hay más de 4 parámetros opcionales.
public class Pizza {{ '{' }}
  private final Size size; private final List<Topping> toppings;
  private Pizza(Builder b) {{ '{' }} this.size=b.size; this.toppings=b.toppings; {{ '}' }}
  public static class Builder {{ '{' }}
    private Size size; private List<Topping> toppings = new ArrayList<>();
    public Builder size(Size s) {{ '{' }} this.size=s; return this; {{ '}' }}
    public Builder topping(Topping t) {{ '{' }} toppings.add(t); return this; {{ '}' }}
    public Pizza build() {{ '{' }} return new Pizza(this); {{ '}' }}
  {{ '}' }}
{{ '}' }}
Pizza p = new Pizza.Builder().size(Size.LARGE).topping(Topping.CHEESE).build();

Prototype

Especifica los tipos de objetos a crear usando una instancia prototípica, y crea nuevos objetos copiando ese prototipo.

Intención
Clonar objetos sin acoplarse a sus clases. El cliente solo necesita la interfaz clone(). Útil cuando la creación es costosa (objeto preconfigurado, conexión establecida).
Cuándo usarlo
Cuando crear un objeto desde cero es más caro que copiarlo. Cuando quieres un "snapshot" del estado de un objeto. Frameworks de Spring usan prototipos para bean scopes.
Deep vs Shallow Copy
La copia superficial (shallow) copia referencias. La copia profunda (deep) copia objetos anidados. Java's Object.clone() hace shallow copy — hay que sobreescribir manualmente.
Java: Cloneable
Java tiene Cloneable + Object.clone(), pero es un diseño defectuoso (lanza checked exception, shallow por defecto). Prefer copy constructor o factory method.
public class Shape {{ '{' }}
  private String color; private int x, y;
  public Shape(Shape source) {{ '{' }} // copy constructor
    this.color = source.color; this.x = source.x; this.y = source.y;
  {{ '}' }}
  public Shape clone() {{ '{' }} return new Shape(this); {{ '}' }}
{{ '}' }}
public class Circle extends Shape {{ '{' }}
  private int radius;
  public Circle(Circle src) {{ '{' }} super(src); this.radius = src.radius; {{ '}' }}
  public Circle clone() {{ '{' }} return new Circle(this); {{ '}' }}
{{ '}' }}
Evaluación — Módulo 1: Patrones Creacionales
dp1q01
¿Cuál es la mejor forma de implementar un Singleton thread-safe en Java moderno?
A synchronized en todo el método getInstance()
B Double-checked locking con volatile
C Un enum con un único valor INSTANCE
D Una variable static final inicializada directamente
Correcto — el Singleton con enum es la forma recomendada por Effective Java (Bloch): thread-safe, serialización segura, y no puede ser roto por reflexión.
Incorrecto — el enum Singleton es la forma más robusta en Java moderno. Es thread-safe, inmune a serialización y reflexión maliciosa.
dp1q02
¿Cuál es el patrón que "deja a las subclases decidir qué clase instanciar"?
A Abstract Factory
B Builder
C Factory Method
D Prototype
Correcto — la definición clásica de Factory Method: "Define an interface for creating an object, but let subclasses decide which class to instantiate."
Incorrecto — Factory Method deja a las subclases decidir qué instanciar. Abstract Factory crea familias de objetos relacionados.
dp1q03
¿Cuál es la principal diferencia entre Factory Method y Abstract Factory?
A Factory Method crea UN producto via herencia; Abstract Factory crea FAMILIAS de productos via composición
B Factory Method usa interfaces; Abstract Factory usa clases abstractas
C Abstract Factory solo funciona con patrones Creacionales; Factory Method con cualquier tipo
D No hay diferencia real entre ambos patrones
Correcto — Factory Method = herencia + 1 producto. Abstract Factory = composición + familia completa de productos relacionados.
Incorrecto — la diferencia clave: Factory Method crea un objeto vía herencia. Abstract Factory crea familias enteras de objetos relacionados vía composición.
dp1q04
¿Qué problema resuelve el patrón Builder en Java?
A Permite crear objetos sin conocer su clase concreta
B Elimina el anti-patrón del constructor telescópico con muchos parámetros opcionales
C Garantiza que solo exista una instancia de la clase
D Permite clonar objetos existentes
Correcto — Builder resuelve la construcción de objetos con muchos parámetros opcionales, haciendo el código legible y evitando el constructor telescópico.
Incorrecto — Builder elimina el problema del constructor con N parámetros (telescoping), permitiendo construir objetos complejos paso a paso.
dp1q05
¿Qué hace @Builder de Lombok?
A Genera automáticamente la clase Builder interna estática con métodos fluentes
B Aplica el patrón Builder al nivel de base de datos
C Crea un Director automático para coordinar la construcción
D Solo funciona con records de Java 14+
Correcto — @Builder de Lombok genera en tiempo de compilación la clase Builder interna con métodos fluentes para todos los campos, más el método build().
Incorrecto — @Builder de Lombok genera el boilerplate del patrón Builder (inner class estática, métodos fluentes, build()) en tiempo de compilación.
dp1q06
¿Cuál es el problema de Object.clone() en Java para implementar Prototype?
A clone() solo funciona con clases final
B Hace copia superficial por defecto, requiere Cloneable (diseño defectuoso) y lanza excepción checked
C No es thread-safe
D No existe Object.clone() en Java
Correcto — Object.clone() tiene varios problemas: shallow copy, Cloneable es un marker interface sin el método, CloneNotSupportedException checked. Se prefiere copy constructor.
Incorrecto — Object.clone() es problemático: shallow copy por defecto, diseño de Cloneable defectuoso, checked exception. Mejor usar constructor copia.
dp1q07
¿Qué rol cumple el Director en el patrón Builder?
A Define el orden de los pasos de construcción y puede reutilizarse para distintos builders
B Es el objeto final que se construye
C Es el cliente que inicia la construcción
D Valida el resultado antes de retornarlo
Correcto — el Director encapsula el algoritmo de construcción (el orden de llamadas a buildPartX). Es opcional: el cliente puede llamar al Builder directamente.
Incorrecto — el Director coordina el proceso de construcción definiendo el orden de pasos. Es independiente del Builder concreto que usa.
dp1q08
¿Cuándo el patrón Singleton viola el principio Single Responsibility?
A Siempre: gestiona tanto su propia creación única como su lógica de negocio
B Solo cuando tiene métodos estáticos
C Cuando implementa una interfaz
D No viola SRP si el constructor es private
Correcto — el Singleton viola SRP porque tiene dos responsabilidades: controlar su instanciación única Y ejecutar su lógica de negocio.
Incorrecto — el Singleton siempre tiene dos responsabilidades: gestionar su unicidad y la lógica de negocio. Viola SRP por definición.
dp1q09
¿Qué garantiza Abstract Factory que Factory Method no garantiza?
A Que el producto sea inmutable
B Que los productos de una familia sean compatibles entre sí
C Que solo exista un objeto de cada tipo
D Que la construcción sea thread-safe
Correcto — Abstract Factory garantiza la consistencia entre productos de la misma familia (ej. botones Windows + checkboxes Windows, nunca mezclados).
Incorrecto — Abstract Factory garantiza que los objetos de una familia sean compatibles entre sí, lo que Factory Method no puede asegurar.
dp1q10
¿Para qué sirve el "Initialization-on-demand holder" pattern en Singleton?
A Lazy initialization thread-safe sin synchronized — la clase interna Holder solo se carga cuando se accede
B Inicializa el Singleton con datos de una base de datos
C Permite múltiples instancias en diferentes ClassLoaders
D Destruye el Singleton cuando ya no se necesita
Correcto — el class loader de Java garantiza que la clase interna Holder se inicialice una sola vez, de forma lazy y thread-safe, sin overhead de sincronización.
Incorrecto — el Initialization-on-demand holder usa la garantía del class loader de Java para obtener lazy initialization thread-safe sin synchronized.
dp1q11
¿En qué se diferencian deep copy y shallow copy en el patrón Prototype?
A Shallow: copia referencias de objetos anidados. Deep: copia recursivamente todos los objetos anidados
B Son equivalentes para objetos sin colecciones
C Deep copy es más rápida que shallow copy
D Shallow copy solo funciona con primitivos
Correcto — shallow copy: dos objetos comparten las mismas referencias internas (modificar uno afecta al otro). Deep copy: objetos completamente independientes.
Incorrecto — shallow: copia el objeto pero comparte referencias internas. Deep: copia todo recursivamente creando objetos completamente independientes.
dp1q12
¿Cuál de estos es un ejemplo real de Factory Method en Java SE?
A new ArrayList<>()
B Calendar.getInstance()
C String.format()
D System.currentTimeMillis()
Correcto — Calendar.getInstance() retorna una subclase concreta de Calendar según la configuración regional — el cliente no sabe qué implementación recibe.
Incorrecto — Calendar.getInstance() es un factory method que retorna una subclase concreta de Calendar (GregorianCalendar, etc.) según el locale.
dp1q13
¿Qué hace el scope prototype de Spring en relación con este patrón?
A Spring crea una nueva instancia del bean cada vez que se inyecta o solicita (no hay instancia compartida)
B Spring clona el bean registrado usando clone()
C Solo aplica a beans con la anotación @Cloneable
D Es equivalente al scope singleton
Correcto — @Scope("prototype") en Spring significa que cada inyección o getBean() crea una nueva instancia, inspirado en el concepto del patrón Prototype (nueva copia por petición).
Incorrecto — el scope prototype de Spring crea una nueva instancia por cada petición/inyección, en contraste con singleton que comparte la misma instancia.
dp1q14
¿Por qué es difícil testear código que usa Singleton directamente?
A No se puede mockear — la dependencia está hardcodeada dentro del método, no puede inyectarse
B JUnit no soporta clases con constructores privados
C El Singleton tiene un ciclo de vida que JUnit no gestiona
D Los métodos estáticos no se pueden llamar desde tests
Correcto — el código que hace ClassX.INSTANCE.method() tiene la dependencia hardcodeada: no se puede sustituir por un mock. La solución es inyectar la dependencia via interfaz.
Incorrecto — el problema es el acoplamiento: Singleton.getInstance() hardcodea la dependencia, imposibilitando la sustitución por mocks en tests.

¿Qué patrón creacional usarías para generar consultas SQL complejas con múltiples cláusulas opcionales?
A Singleton

B Builder
D Prototype

Incorrecto — Builder es el patrón ideal para objetos complejos con muchas partes opcionales, como consultas SQL. QueryDSL y JPA Criteria API lo usan.
dp1q16
¿Cuál es la diferencia entre un static factory method y el patrón Factory Method GoF?
A Static factory method es un método estático de conveniencia; Factory Method GoF es un patrón con herencia y polimorfismo
B Son lo mismo — el GoF usa métodos estáticos
C Static factory method solo existe en Effective Java, no en GoF
D Factory Method GoF siempre retorna un Singleton
Correcto — static factory method (Bloch) = método estático que crea objetos (List.of()). Factory Method GoF = patrón de herencia donde subclases deciden qué instanciar.
Incorrecto — son conceptos distintos: static factory method es un idioma de implementación; Factory Method GoF es un patrón de diseño basado en herencia.
dp1q17
¿Qué ventaja tiene el patrón Abstract Factory para cambiar de "familia" en producción?
A Basta con cambiar la implementación concreta de la factory — el código cliente no cambia
B Requiere cambiar solo los productos, no la factory
C No es posible cambiar de familia en producción
D Hay que modificar todos los clientes que usan los productos
Correcto — el cliente trabaja con GUIFactory abstracta. Pasar WinFactory o MacFactory es la única diferencia. El OCP se cumple perfectamente.
Incorrecto — con Abstract Factory basta con cambiar la implementación concreta de la factory para cambiar toda la familia de objetos. El cliente no toca.

dp1q19
¿Cuándo NO usar el patrón Builder?
A Cuando el objeto tiene pocos parámetros (2-3) todos requeridos — añade complejidad innecesaria
B Cuando el objeto es immutable
C Cuando el objeto necesita validación

Incorrecto — Builder agrega complejidad. Si el objeto tiene 2-3 parámetros todos requeridos, un simple constructor es más claro y preferible.
