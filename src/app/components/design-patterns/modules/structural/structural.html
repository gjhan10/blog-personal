Adapter

Convierte la interfaz de una clase en otra que el cliente espera. Permite que clases con interfaces incompatibles trabajen juntas.

Intención
El Adapter "envuelve" al Adaptee y traduce las llamadas del cliente. Es el "enchufe adaptador" del software: permite conectar interfaces incompatibles.
Cuándo usarlo
Cuando quieres usar una clase existente con una interfaz incompatible. Integración con librerías de terceros. Legacy code que no puedes modificar.
Object vs Class Adapter
Object Adapter (composición): delega al Adaptee — más flexible. Class Adapter (herencia múltiple): Java no lo soporta directamente, pero puede usar herencia de Adaptee.
Ejemplos en Java
Arrays.asList(), Collections.list(), InputStreamReader (adapta InputStream a Reader), BufferedReader. Spring usa Adapters en HandlerAdapter (MVC).
// Adaptee (legacy, no podemos modificar)
class XmlParser {{ '{' }} public Document parseXml(String xml) {{ '{' }} ... {{ '}' }} {{ '}' }}
interface Parser {{ '{' }} Map parse(String data); {{ '}' }} // Target
class XmlParserAdapter implements Parser {{ '{' }} // Adapter
  private final XmlParser adaptee = new XmlParser();
  public Map parse(String data) {{ '{' }}
    Document doc = adaptee.parseXml(data); // traduce la llamada
    return convertToMap(doc);
  {{ '}' }}

Bridge

Desacopla una abstracción de su implementación para que ambas puedan variar independientemente.

Intención
Separa la jerarquía de abstracción (Shape) de la jerarquía de implementación (Renderer). Ambas pueden crecer independientemente sin explosión combinatoria de subclases.
Cuándo usarlo
Cuando tienes N tipos × M implementaciones y evitar N×M subclases. Cuando quieres cambiar la implementación en tiempo de ejecución. Cuando ambas jerarquías deben ser extensibles.
Abstracción vs Implementación
Abstracción: la interfaz de alto nivel (Shape — qué se hace). Implementación: cómo se hace (Renderer — VectorRenderer/RasterRenderer). La Abstracción delega en la Implementación.
vs Adapter
Adapter: hace que cosas incompatibles trabajen juntas (corrección). Bridge: diseña desde el inicio para que abstracción e implementación varíen libremente (previsión).
interface Renderer {{ '{' }} void renderCircle(float x, float y, float r); {{ '}' }}
abstract class Shape {{ '{' }}
  protected final Renderer renderer; // el "bridge"
  protected Shape(Renderer r) {{ '{' }} this.renderer = r; {{ '}' }}
  abstract void draw();
{{ '}' }}
class Circle extends Shape {{ '{' }}
  private float x, y, radius;
  public void draw() {{ '{' }} renderer.renderCircle(x, y, radius); {{ '}' }}
{{ '}' }}
// Uso: Circle con VectorRenderer o RasterRenderer sin más subclases
var c = new Circle(new VectorRenderer());
3M2 · Estructurales

Composite

Compone objetos en estructuras de árbol para representar jerarquías parte-todo. Permite tratar objetos individuales y composiciones uniformemente.

Intención
El cliente trata Leaf y Composite de la misma forma. Composite contiene una colección de Component (que puede ser Leaf o Composite). Estructura recursiva en árbol.
Cuándo usarlo
Sistemas de archivos (File y Folder), UI components, árboles de menú, estructuras de datos jerárquicas, parsers de expresiones. Siempre que tengas jerarquías parte-todo.
Leaf vs Composite
Leaf: nodo hoja sin hijos, hace el trabajo real. Composite: nodo rama con hijos, delega en sus hijos con for (Component c : children) c.execute().
Dilema de diseño
Si add/remove están en Component, Leaf tiene métodos que no usa (viola ISP). Si están solo en Composite, el cliente debe hacer cast. Se prefiere tenerlos en Component con implementación vacía en Leaf.
interface FileSystemItem {{ '{' }} void display(String indent); {{ '}' }}
record FileItem(String name) implements FileSystemItem {{ '{' }}
  public void display(String indent) {{ '{' }} System.out.println(indent + name); {{ '}' }}
{{ '}' }}
class Directory implements FileSystemItem {{ '{' }}
  private final List<FileSystemItem> children = new ArrayList<>();
  void add(FileSystemItem item) {{ '{' }} children.add(item); {{ '}' }}
  public void display(String indent) {{ '{' }}
    System.out.println(indent + name + "/");
    children.forEach(c -> c.display(indent + " "));
  {{ '}' }}

Decorator

Añade responsabilidades adicionales a un objeto dinámicamente. Los decoradores son una alternativa flexible a la herencia para extender funcionalidad.

Intención
Envuelve un objeto en otro que añade comportamiento. Puede apilarse: new TLS(new Compression(new DataSource())). Cada capa añade algo antes/después de delegar.
Cuándo usarlo
Cuando extender con herencia es impráctcio (clases final, explosión de subclases). Añadir/quitar comportamiento dinámicamente. Java I/O streams son el ejemplo canónico.
Java I/O Streams
new BufferedReader(new InputStreamReader(new FileInputStream("f.txt"))) es Decorator en acción: cada nivel añade buffering, charset conversion, file reading.
vs Herencia
Herencia: comportamiento extra en tiempo de compilación. Decorator: en tiempo de ejecución, más flexible. Pero Decorator puede complicar debugging (múltiples capas de wrapping).
interface TextTransformer {{ '{' }} String transform(String text); {{ '}' }}
class PlainText implements TextTransformer {{ '{' }}
  public String transform(String t) {{ '{' }} return t; {{ '}' }}
{{ '}' }}
abstract class TextDecorator implements TextTransformer {{ '{' }}
  protected final TextTransformer wrapped;
  protected TextDecorator(TextTransformer w) {{ '{' }} this.wrapped = w; {{ '}' }}
{{ '}' }}
class UpperCaseDecorator extends TextDecorator {{ '{' }}
  public String transform(String t) {{ '{' }} return wrapped.transform(t).toUpperCase(); {{ '}' }}

Facade

Proporciona una interfaz simplificada a un subsistema complejo. El cliente solo necesita conocer la fachada.

Intención
Oculta la complejidad interna del subsistema detrás de una interfaz simple. El cliente no necesita conocer los detalles del subsistema — solo la Facade.
Cuándo usarlo
Cuando tienes un subsistema complejo con muchas clases. Para organizar código en capas. Para crear un punto de entrada a una librería o API. Para reducir dependencias externas.
Ejemplos en Spring
JdbcTemplate es una Facade sobre JDBC (DataSource, Connection, PreparedStatement, ResultSet). RestTemplate oculta la complejidad de HTTP. SLF4J oculta la librería de logging.
Anti-patrón: God Facade
Cuidado con Facades que crecen demasiado y se convierten en una clase "God" que sabe demasiado. Una Facade debe simplificar, no acumular toda la lógica de negocio.
class HomeTheaterFacade {{ '{' }}
  private final Projector proj; private final SoundSystem sound; private final Lights lights;
  public void watchMovie(String movie) {{ '{' }}
    lights.dim(10);
    proj.on(); proj.setInput(Input.HDMI);
    sound.setSurroundSound(); sound.setVolume(5);
    proj.play(movie);
  {{ '}' }}
  public void endMovie() {{ '{' }} proj.off(); sound.off(); lights.on(); {{ '}' }}
{{ '}' }}
// Cliente: solo necesita saber watchMovie/endMovie

Flyweight

Usa el compartir para soportar eficientemente un gran número de objetos de grano fino, reduciendo el consumo de memoria.

Intención
Divide el estado del objeto en intrínseco (compartido, inmutable) y extrínseco (único por uso, pasado como parámetro). La Factory cachea los objetos intrínsecos.
Cuándo usarlo
Cuando necesitas millones de objetos similares (partículas en juegos, caracteres en editor de texto, píxeles en gráficos). Cuando el coste de memoria es crítico.
Java: String Pool e Integer Cache
Java implementa Flyweight en String.intern() (String pool) y en el caché de Integer/Long para valores entre -128 y 127. Integer.valueOf(127) == Integer.valueOf(127) es true.
Complejidad vs Beneficio
El patrón añade complejidad (factory, split de estado). Solo vale la pena cuando el ahorro de memoria es medible. RAM es barata hoy — solo aplicar con millones de objetos.

Proxy

Proporciona un sustituto o placeholder de otro objeto para controlar el acceso al mismo.

Tipos de Proxy
Virtual: lazy loading (crea el objeto caro solo cuando se necesita). Protection: control de acceso. Remote: objeto en otro proceso/servidor. Caching: cachea resultados.
Cuándo usarlo
Lazy initialization de objetos costosos. Logging o auditoría transparente. Cache de resultados de operaciones caras. Control de acceso basado en permisos. Spring AOP usa proxies.
Dynamic Proxy en Java
java.lang.reflect.Proxy crea proxies dinámicos en tiempo de ejecución. Spring AOP, JPA Lazy Loading (Hibernate) y CDI usan dynamic proxies o CGLIB para intercepción.
vs Decorator
Proxy y Decorator tienen estructura similar, pero propósito distinto. Proxy controla el acceso al objeto real. Decorator añade comportamiento sin restricciones de acceso.
interface Image {{ '{' }} void display(); {{ '}' }}
class RealImage implements Image {{ '{' }}
  private final String file;
  RealImage(String f) {{ '{' }} this.file = f; loadFromDisk(); {{ '}' }} // costoso
  public void display() {{ '{' }} System.out.println("Displaying " + file); {{ '}' }}
{{ '}' }}
class ProxyImage implements Image {{ '{' }} // Virtual Proxy
  private RealImage real; private final String file;
  public void display() {{ '{' }}
    if (real == null) real = new RealImage(file); // lazy init
    real.display();
  {{ '}' }}
{{ '}' }}
Evaluación — Módulo 2: Patrones Estructurales
dp2q01
¿Qué componente del patrón Adapter "envuelve" al Adaptee?
A El Target
B El Client
C El Adapter
D El Facade
Correcto — el Adapter contiene (o hereda de) el Adaptee y traduce las llamadas de la interfaz Target a las operaciones del Adaptee.
Incorrecto — el Adapter es quien envuelve al Adaptee y traduce las llamadas del cliente (Target interface) a la API incompatible del Adaptee.
dp2q02
¿Cuál es el ejemplo canónico del patrón Decorator en Java SE?
A Collections.unmodifiableList()
B new BufferedReader(new InputStreamReader(new FileInputStream(...)))
C String.format()
D Calendar.getInstance()
Correcto — Java I/O usa Decorator extensamente: FileInputStream (datos crudos) → InputStreamReader (convierte bytes a chars) → BufferedReader (añade buffer). Cada capa agrega comportamiento.
Incorrecto — las Java I/O Streams son el ejemplo canónico de Decorator: cada wrapper añade un comportamiento sobre el anterior (buffering, charset, etc.).
dp2q03
¿Qué problema resuelve el Bridge que no resuelve la herencia simple?
A Evita la explosión combinatoria de subclases cuando hay N abstracciones × M implementaciones
B Permite usar interfaces en lugar de clases abstractas
C Permite crear objetos sin constructores públicos
D Hace el código thread-safe automáticamente
Correcto — con herencia: 3 formas × 3 renderizados = 9 clases. Con Bridge: 3 + 3 = 6 clases. La composición escala mejor que la herencia múltiple.
Incorrecto — Bridge evita la explosión combinatoria N×M de subclases separando abstracción e implementación en jerarquías independientes.
dp2q04
¿Cuál es la diferencia entre Composite y una simple lista de objetos?
A Composite trata Leaf y Composite con la misma interfaz — el cliente no necesita saber si es un nodo hoja o rama
B Composite solo permite objetos del mismo tipo
C Una lista es más eficiente que Composite en todos los casos
D Composite no puede contener más de un nivel de profundidad
Correcto — la uniformidad es la clave: con Composite, el cliente hace myComponent.execute() sin saber si es una hoja o un árbol entero. La recursión queda oculta.
Incorrecto — Composite usa una interfaz uniforme para Leaf y Composite. El cliente puede llamar execute() en cualquier nodo sin importar si tiene hijos o no.
dp2q05
¿Qué es el estado intrínseco en el patrón Flyweight?
A El estado inmutable y compartido entre múltiples objetos (ej. la fuente y el color de un carácter)
B El estado que cambia con cada uso del objeto (ej. la posición del carácter)
C El estado almacenado en la Flyweight Factory
D El estado de la JVM en tiempo de ejecución
Correcto — intrínseco = compartido, inmutable (fuente, tamaño, color). Extrínseco = único por instancia, pasado como parámetro (posición x,y del carácter).
Incorrecto — el estado intrínseco es el compartido/inmutable. El extrínseco es el que varía por cada uso y se pasa como parámetro al método de operación.
dp2q06
¿Por qué Spring AOP usa Proxy internamente?
A Para interceptar llamadas a métodos y añadir comportamiento cross-cutting (logging, transacciones) de forma transparente
B Para crear múltiples instancias del bean original
C Para serializar beans a JSON automáticamente
D Para encriptar los datos del bean
Correcto — Spring envuelve los beans en proxies JDK o CGLIB. Al llamar un método @Transactional, el proxy intercepta, abre la transacción, ejecuta, y la confirma/rollback.
Incorrecto — Spring AOP usa Proxy para interceptar métodos y añadir comportamiento transversal (@Transactional, @Cacheable, @Secured) sin modificar el código del bean.
dp2q07
¿Cuál es la diferencia entre Facade y Adapter?
A Facade simplifica un subsistema complejo; Adapter hace compatibles dos interfaces incompatibles
B Son el mismo patrón con nombres distintos
C Adapter trabaja con subsistemas; Facade con objetos individuales
D Facade siempre usa herencia; Adapter siempre usa composición
Correcto — Facade: simplifica (ocultando complejidad de N clases). Adapter: traduce (convierte interfaz incompatible en compatible). Objetivo diferente.
Incorrecto — Facade = simplificación de subsistema complejo. Adapter = traducción entre interfaces incompatibles. Propósitos distintos aunque estructuralmente similares.
dp2q08
¿Cómo implementa Java el patrón Flyweight en sus tipos primitivos envueltos?
A Integer.valueOf() cachea instancias para valores entre -128 y 127 — reutiliza el mismo objeto
B Todos los Integer son singletons
C Java usa autoboxing con deep copy para Integer
D Integer.valueOf() siempre crea una nueva instancia
Correcto — Integer, Byte, Short, Long cachean valores [-128, 127]. Integer.valueOf(100) == Integer.valueOf(100) es true. Fuera del rango, new Integer() crea instancias nuevas.
Incorrecto — Integer.valueOf() usa un caché interno para [-128, 127], reutilizando instancias (Flyweight). Por eso == funciona en ese rango pero no fuera de él.
dp2q09
¿En qué se parecen Proxy y Decorator estructuralmente?
A Ambos implementan la misma interfaz que el objeto envuelto y añaden comportamiento pre/post llamada
B Ambos requieren herencia múltiple
C Ambos crean objetos sin constructores
D Solo se diferencian en el nombre
Correcto — ambos patrones envuelven un objeto e implementan su interfaz. La diferencia es el propósito: Proxy controla acceso, Decorator agrega funcionalidad.
Incorrecto — estructuralmente son casi idénticos (ambos envuelven e implementan la misma interfaz), pero su intención difiere: Proxy = control de acceso, Decorator = extensión.
dp2q10
¿Cuándo usarías Adapter en vez de modificar el código legacy directamente?
A Cuando el código legacy es de una librería de terceros que no puedes modificar
B Cuando el código legacy es tuyo y tienes tiempo
C Cuando el código legacy no tiene tests
D Nunca — siempre es mejor modificar el código fuente
Correcto — Adapter es esencial para integración con librerías externas (JAR sin fuente), APIs legacy de terceros, o código que no debes romper porque otros lo usan.
Incorrecto — Adapter es la solución cuando no puedes modificar el código fuente (librería externa, API de terceros, código legacy crítico sin tests).
dp2q11
¿Qué patrón estructural usa JdbcTemplate de Spring?
A Adapter
B Facade
C Proxy
D Bridge
Correcto — JdbcTemplate es una Facade sobre el complejo API de JDBC: oculta Connection, PreparedStatement, ResultSet, manejo de excepciones checked, etc.
Incorrecto — JdbcTemplate es una Facade que simplifica JDBC: el cliente solo llama query() o update() sin gestionar Connection, PreparedStatement, ni excepciones JDBC directamente.
dp2q12
¿Cuál es la estructura de árbol que representa el patrón Composite?
A Árbol binario balanceado
B Árbol N-ario donde Leaf no tiene hijos y Composite tiene una lista de Component
C Árbol donde todos los nodos son del mismo tipo concreto
D Grafo dirigido acíclico
Correcto — Composite forma un árbol N-ario recursivo: Composite tiene List<Component> (cada Component puede ser Leaf o Composite), y Leaf es el nodo terminal.
Incorrecto — Composite crea un árbol N-ario donde Composite contiene List<Component>. Cada Component puede ser Leaf (nodo final) o Composite (nodo rama con hijos).
dp2q13
¿Cuál es el tipo de Proxy que evita crear un objeto costoso hasta que realmente se necesita?
A Virtual Proxy
B Protection Proxy
C Remote Proxy
D Caching Proxy
Correcto — Virtual Proxy implementa lazy initialization: el objeto costoso (base de datos, imagen grande) solo se crea cuando se llama al método por primera vez.
Incorrecto — Virtual Proxy hace lazy initialization del objeto real: lo crea solo cuando se accede por primera vez. Hibernate usa este patrón para relaciones lazy.
dp2q14
¿Cuántos objetos concretos se crearían con 4 formas × 3 renderizadores usando Bridge?
A 12 (4 × 3)
B 7 (4 + 3)
C 1 (solo se necesita un objeto)
D 24 (4 × 3 × 2)
Correcto — con Bridge: 4 subclases de Shape + 3 implementaciones de Renderer = 7 clases. Sin Bridge: 12 subclases (Circle_Vector, Circle_Raster, etc.).
Incorrecto — Bridge reduce N×M a N+M: 4 formas + 3 renderizadores = 7 clases en lugar de 12. La composición escala linealmente en vez de cuadráticamente.

¿Qué hace InputStreamReader en relación con los patrones GoF?
A Es un Adapter que adapta InputStream (bytes) a Reader (chars)
B Es un Decorator que añade funcionalidad a InputStream
C Es una Facade sobre el sistema de archivos
D Es un Proxy de seguridad para streams
Correcto — InputStreamReader es un Adapter: convierte la interfaz InputStream (bytes) en Reader (chars), adaptando la API incompatible sin modificarla.
Incorrecto — InputStreamReader es un Adapter que convierte InputStream (bytes) a Reader (chars). Las clases Java I/O usan tanto Adapter como Decorator.
dp2q16
¿Por qué el patrón Flyweight requiere que el estado intrínseco sea inmutable?
A Porque el objeto se comparte entre múltiples contextos — modificarlo afectaría a todos los usuarios
B Porque Java no permite modificar variables estáticas
C Para facilitar la serialización
D Por requisito del compilador de Java
Correcto — si el estado compartido fuera mutable, cambiar el color de UN carácter cambiaría el color de TODOS los caracteres que usan ese mismo estilo. La inmutabilidad es fundamental.
Incorrecto — el estado intrínseco debe ser inmutable porque es compartido. Si fuera mutable, cambiar el estado en un contexto afectaría a todos los otros contextos que comparten el mismo flyweight.
dp2q17
¿Cómo difiere el propósito de Adapter del propósito de Bridge?
A Adapter arregla incompatibilidades existentes; Bridge se diseña desde el principio para variación independiente
B Bridge es solo para APIs de red; Adapter para APIs locales
C Son equivalentes y se pueden intercambiar
D Adapter usa herencia; Bridge solo usa composición
Correcto — Adapter es reactivo (arregla incompatibilidad ya existente). Bridge es proactivo (diseño para extensibilidad futura de ambas jerarquías).
Incorrecto — Adapter soluciona incompatibilidades después del hecho. Bridge se diseña a priori para que abstracción e implementación evolucionen de forma independiente.
dp2q18
¿Qué es Hibernate Lazy Loading en términos de patrones GoF?
A Virtual Proxy — Hibernate crea un proxy de la entidad que carga los datos de la BD solo al acceder
B Decorator — añade comportamiento de carga lazy a la entidad
C Flyweight — comparte entidades entre sesiones
D Facade — simplifica la carga de relaciones
Correcto — Hibernate genera subclases proxy (CGLIB/ByteBuddy) de las entidades. Al acceder a una relación lazy, el proxy intercepta y ejecuta la query SQL.
Incorrecto — Hibernate lazy loading usa Virtual Proxy: genera un proxy de la entidad que solo ejecuta la SELECT de la BD cuando se accede a la propiedad por primera vez.
dp2q19
¿Cuántas capas de Decorator se pueden apilar en teoría?
A Máximo 3, es el límite recomendado por GoF
B Ilimitadas — cualquier número, ya que todos implementan la misma interfaz
C Solo 2 — el objeto real y un decorator
D Depende del compilador de Java
Correcto — la recursividad del patrón permite N capas. Cada Decorator tiene la misma interfaz, por lo que puede envolverse infinitamente. La práctica limita a las capas necesarias.
Incorrecto — se pueden apilar tantos Decorators como se necesite, ya que todos implementan la misma interfaz Component. No hay límite técnico.
dp2q20
¿Qué patrón estructural usarías para implementar control de acceso a métodos según roles de usuario?
A Facade
B Composite
C Proxy (Protection Proxy)
D Flyweight
Correcto — Protection Proxy controla el acceso verificando permisos antes de delegar. Spring Security con @PreAuthorize usa este patrón a través de AOP proxies.
