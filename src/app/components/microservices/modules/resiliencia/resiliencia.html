Circuit Breaker con Resilience4j

El Circuit Breaker previene la propagación de fallos en cascada. Cuando un servicio destino falla repetidamente, el circuito "abre" y las llamadas subsiguientes se rechazan inmediatamente sin esperar el timeout.

Estado CLOSED
Operación normal. Las llamadas pasan al servicio. Se monitorizan fallos y latencias. Si la tasa de error supera el umbral, el circuito abre.
Estado OPEN
Las llamadas fallan inmediatamente sin contactar el servicio (fail-fast). Se ejecuta el fallback. Después de waitDurationInOpenState, pasa a HALF_OPEN.
Estado HALF_OPEN
Se permiten N llamadas de prueba. Si tienen éxito, el circuito cierra. Si fallan, vuelve a OPEN. Permite recuperación automática sin intervención manual.
Sliding Window
Resilience4j usa ventana deslizante (COUNT_BASED o TIME_BASED) para calcular la tasa de error. Es más preciso que un simple contador de fallos consecutivos.
# application.yml
resilience4j.circuitbreaker.instances.inventory:
  slidingWindowSize: 10
  failureRateThreshold: 50
  waitDurationInOpenState: 10s
  permittedNumberOfCallsInHalfOpenState: 3
// Java — anotación
@CircuitBreaker(name = "inventory", fallbackMethod = "fallbackStock")
public Stock getStock(String id) {{ '{' }} return inventoryClient.get(id); {{ '}' }}
private Stock fallbackStock(String id, Exception e) {{ '{' }} return Stock.empty(); {{ '}' }}

Bulkhead Pattern

El patrón Bulkhead (mamparo de barco) aísla los recursos por funcionalidad. Si las llamadas al servicio A saturan el thread pool, el servicio B sigue funcionando normalmente con su propio pool.

Semaphore Bulkhead
Limita el número de llamadas concurrentes con un semáforo. Más ligero en recursos. Cuando el semáforo está lleno, las llamadas adicionales reciben un fallback inmediatamente.
Thread Pool Bulkhead
Ejecuta las llamadas en un pool dedicado de threads. Permite timeout verdadero y aislamiento completo. Mayor overhead de contexto pero más robusto para I/O bloqueante.
Cuándo usar cada uno
Semaphore: operaciones no bloqueantes o reactivas. Thread Pool: llamadas síncronas que pueden bloquearse, donde necesitas timeout real y aislamiento de CPU.
Combinado con CB
Bulkhead + Circuit Breaker = defensa en profundidad. El Bulkhead evita que una dependencia lenta consuma todos los threads; el CB evita llamadas cuando la dependencia falla.
# Bulkhead de semáforo
resilience4j.bulkhead.instances.inventory:
  maxConcurrentCalls: 10
  maxWaitDuration: 0
// Anotación combinada
@Bulkhead(name = "inventory", type = Bulkhead.Type.SEMAPHORE)
@CircuitBreaker(name = "inventory")
public Stock getStock(String id) {{ '{' }} ... {{ '}' }}

Retry & Fallback

El Retry automático maneja fallos transitorios (red inestable, servicio reiniciando). El exponential backoff con jitter evita el "thundering herd" cuando múltiples clientes reintentan simultáneamente.

Exponential Backoff
El tiempo de espera entre reintentos se duplica: 100ms, 200ms, 400ms. Reduce la presión sobre un servicio en recuperación sin saturarlo con reintentos agresivos.
Jitter (aleatoriedad)
Añade un componente aleatorio al backoff. Sin jitter, todos los clientes que fallaron simultáneamente reintentarían al mismo tiempo. El jitter los distribuye en el tiempo.
Excepciones a reintentar
Solo reintentar excepciones transitorias: timeout, 503, network error. NUNCA reintentar errores de negocio (400, 404) ya que el reintento no cambiará el resultado.
Fallback
Respuesta alternativa cuando el servicio no está disponible: retornar datos en caché, un valor por defecto o una respuesta degradada que permita al usuario continuar.
# Retry con backoff
resilience4j.retry.instances.inventory:
  maxAttempts: 3
  waitDuration: 500ms
  enableExponentialBackoff: true
  exponentialBackoffMultiplier: 2
  retryExceptions: [java.net.ConnectException, feign.RetryableException]
  ignoreExceptions: [com.example.BusinessException]

Timeout Patterns

Sin timeouts, una dependencia lenta puede retener threads indefinidamente, agotando el pool y haciendo que todo el servicio deje de responder. Los timeouts son la primera línea de defensa.

Connection Timeout
Tiempo máximo para establecer la conexión TCP. Si el servidor no responde en este tiempo, se lanza un ConnectTimeoutException. Típicamente 1-5 segundos.
Read Timeout
Tiempo máximo para recibir datos una vez conectado. Si el servidor acepta la conexión pero no envía respuesta en este tiempo, se lanza ReadTimeoutException.
Resilience4j TimeLimiter
Complementa los timeouts de red con un timeout de ejecución más fino. Útil cuando el cliente HTTP no expone bien los timeouts o para limitar código asíncrono.
Timeout Budget
En cadenas de servicios, el timeout de cada llamada debe ser menor que el timeout del servicio padre. Si A tiene 3s, B (llamado por A) debe tener <3s para dejar margen.
// Timeout en Feign Client
feign.client.config.inventory-service:
  connectTimeout: 2000
  readTimeout: 5000
// Resilience4j TimeLimiter
resilience4j.timelimiter.instances.inventory:
  timeoutDuration: 3s
  cancelRunningFuture: true

Rate Limiting

El Rate Limiting protege los servicios de sobrecarga limitando el número de peticiones que un cliente puede hacer en un período de tiempo. Es esencial tanto en el API Gateway como en servicios individuales.

Token Bucket
Los tokens se añaden al cubo a una tasa constante. Cada petición consume un token. Permite bursts hasta la capacidad del cubo. El algoritmo más usado por su flexibilidad.
Leaky Bucket
Las peticiones salen a una tasa constante independientemente del ritmo de entrada. Suaviza los picos de tráfico pero puede introducir latencia en peticiones que esperan en la cola.
Fixed Window
Limita N peticiones por ventana de tiempo fija. Simple pero vulnerable al "double burst": N peticiones al final de una ventana + N al inicio de la siguiente.
Sliding Window Log
Rastrea el timestamp de cada petición. Más preciso que Fixed Window pero requiere más memoria. Ideal para límites estrictos donde la exactitud es crítica.
# Resilience4j RateLimiter
resilience4j.ratelimiter.instances.orders-api:
  limitForPeriod: 100
  limitRefreshPeriod: 1s
  timeoutDuration: 0
@RateLimiter(name = "orders-api", fallbackMethod = "rateLimitFallback")
public OrderDto createOrder(OrderRequest req) {{ '{' }} ... {{ '}' }}

Chaos Engineering

Chaos Engineering es la disciplina de experimentar deliberadamente sobre un sistema en producción para descubrir debilidades antes de que lo hagan los fallos reales. Popularizado por Netflix con Chaos Monkey.

1
Define el estado estable: métricas que indican que el sistema funciona correctamente (latencia p99, error rate, throughput).
2
Genera la hipótesis: "Si el servicio de pagos tiene 200ms de latencia extra, el checkout seguirá funcionando".
3
Introduce variables reales: latencia, errores, pérdida de paquetes, kill de instancias, agotamiento de disco.
4
Observa si el sistema regresa al estado estable. Si no, encontraste una debilidad real.
5
Minimiza el radio de blast: empieza en staging, luego un pequeño porcentaje de producción (con feature flags).
Chaos Monkey for Spring Boot
Librería que inyecta fallos en beans de Spring: latencia, excepciones, kill de instancias. Configurable por perfil para no afectar producción.
Chaos Mesh (Kubernetes)
Plataforma de chaos engineering para Kubernetes. Inyecta fallos de red, CPU stress, memory pressure y pod failures a nivel de contenedor sin modificar el código.
Chaos Engineering no es "romper cosas aleatoriamente". Es experimentación científica controlada para validar la resiliencia y encontrar puntos débiles antes que los usuarios.
