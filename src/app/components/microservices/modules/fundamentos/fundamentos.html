01M1 · Fundamentos

¿Qué son los Microservicios?

Una arquitectura de microservicios descompone una aplicación en servicios pequeños, autónomos y desplegables de forma independiente, cada uno responsable de una capacidad de negocio específica.

Monolito
Un único artefacto desplegable
Toda la lógica en un proceso
Escalado todo-o-nada
Un fallo puede tumbar todo
Deploy lento y riesgoso
Un stack tecnológico forzado
Microservicios
Múltiples servicios independientes
Cada servicio = un proceso
Escalado selectivo por servicio
Fallos aislados (fault isolation)
Deploy independiente y rápido
Polyglot: cada servicio elige su tech
Autonomía
Cada servicio puede ser desarrollado, desplegado y escalado de forma independiente. Los equipos poseen su servicio end-to-end.
Base de datos por servicio
Cada microservicio tiene su propia base de datos (o schema). Esto garantiza el acoplamiento débil y permite elegir la tecnología adecuada para cada dominio.
Comunicación vía API
Los servicios se comunican únicamente a través de APIs bien definidas (REST, gRPC, eventos). No comparten código interno ni base de datos.
Complejidad operacional
A cambio de flexibilidad, se incrementa la complejidad: observabilidad distribuida, consistencia eventual, latencia de red y gestión de muchos servicios.
Los microservicios no son una solución universal. Para equipos pequeños o dominios simples, un monolito bien estructurado (modular monolith) suele ser más apropiado.
02M1 · Fundamentos

Bounded Context & DDD

El Domain-Driven Design (DDD) proporciona las herramientas conceptuales para identificar los límites naturales entre microservicios a través del concepto de Bounded Context.

Bounded Context
Un límite explícito dentro del cual un modelo de dominio es válido y consistente. El mismo término ("Pedido") puede tener significados distintos en el contexto de Ventas y de Logística.
Ubiquitous Language
Vocabulario compartido entre desarrolladores y expertos del dominio dentro de un Bounded Context. Reduce la ambigüedad y alinea el código con el negocio.
Aggregate
Un grupo de objetos de dominio que se tratan como una unidad. El Aggregate Root es el único punto de entrada para modificar el estado. Por ejemplo: Order con sus OrderLines.
Context Map
Diagrama que muestra cómo los distintos Bounded Contexts se relacionan: Shared Kernel, Customer-Supplier, Conformist, Anti-Corruption Layer, etc.

03M1 · Fundamentos

Patrones de Descomposición

Cómo dividir un monolito en microservicios usando estrategias basadas en el dominio de negocio.

Por capacidad de negocio
Cada servicio implementa una capacidad estable del negocio: Gestión de pedidos, Gestión de usuarios, Procesamiento de pagos. Las capacidades cambian poco con el tiempo.
Por subdominio (DDD)
Identifica subdominios Core (ventaja competitiva), Supporting (apoya el negocio) y Generic (commodities). Los servicios core merecen más inversión.
Strangler Fig Pattern
Migración incremental del monolito. Se añade un proxy que redirige gradualmente tráfico al nuevo microservicio, hasta que el monolito queda vacío y se elimina.
Anti-patrones a evitar
Nanoservicios (demasiado granulares), servicios chatty (muchas llamadas síncronas entre sí), shared database (acoplamiento alto) y distributed monolith.

04M1 · Fundamentos

Comunicación síncrona vs asíncrona

La elección entre comunicación síncrona (REST/gRPC) y asíncrona (mensajería/eventos) tiene profundas implicaciones en la resiliencia y el acoplamiento entre servicios.

Síncrona (REST/gRPC)
Requiere que el receptor esté disponible
Acoplamiento temporal
Fácil de depurar con trazas HTTP
Simple para queries y comandos inmediatos
Cascada de fallos posible
Latencia acumulada en cadenas
Asíncrona (Kafka/RabbitMQ)
Receptor puede estar caído temporalmente
Desacoplamiento temporal
Más compleja de depurar (correlationId)
Ideal para flujos de trabajo largos
Fallos aislados automáticamente
Mayor throughput y resiliencia
Cuándo usar síncrona
Consultas que requieren respuesta inmediata (leer un perfil, verificar stock), operaciones que necesitan confirmación antes de continuar, llamadas simples de bajo acoplamiento.
Cuándo usar asíncrona
Notificaciones (email, SMS), procesos de negocio largos (checkout → pago → envío), integración entre dominios distintos, operaciones que toleran eventual consistency.
05M1 · Fundamentos

API Design First (OpenAPI)

Diseñar el contrato de la API antes de implementarla mejora la colaboración entre equipos y garantiza interfaces estables. OpenAPI 3.x es el estándar de facto.

1
Define el contrato en openapi.yml con paths, schemas y respuestas.
2
Genera código servidor/cliente con OpenAPI Generator o springdoc-openapi.
3
Usa Contract Testing (Pact) para verificar que consumidor y productor cumplen el contrato.
4
Versiona las APIs con URL versioning (/v1/orders) o headers (Accept: application/vnd.api+json;version=2).
5
Publica el contrato en un API Registry (Backstage, Apicurio) para descubrimiento.
# openapi.yml
openapi: "3.0.3"
paths:
  /orders/{{ '{' }}id{{ '}' }}:
    get:
      operationId: getOrder
      responses:
        "200":
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/OrderDto'
06M1 · Fundamentos

Challenges & Anti-patrones

Los microservicios resuelven problemas de escala y autonomía, pero introducen complejidad que debe gestionarse activamente para no crear un "Distributed Monolith".

Distributed Monolith
Servicios que están desplegados separados pero tienen acoplamiento alto: base de datos compartida, deploys coordinados obligatorios, fallos en cascada. El peor de ambos mundos.
Servicios Chatty
Un flujo de negocio requiere 10+ llamadas síncronas encadenadas entre servicios. Solución: agregar datos (BFF, GraphQL) o cambiar a comunicación asíncrona.
Consistencia Eventual
Sin transacciones distribuidas, la consistencia entre servicios es eventual. Hay que diseñar para ello: idempotencia, reintentos, compensación (Saga).
Observabilidad
Sin trazas distribuidas, logs correlacionados y métricas por servicio, depurar un problema que atraviesa 5 servicios es casi imposible en producción.
Regla de oro: empieza con un monolito modular. Extrae microservicios cuando tengas límites claros, equipos separados o necesidades de escalado independiente.
