REST entre microservicios

Spring 6 introdujo RestClient como sucesor de RestTemplate. Para microservicios con Eureka, Spring Cloud LoadBalancer enruta las peticiones automáticamente.

RestClient (Spring 6)
API fluida y síncrona, sucesor directo de RestTemplate. Ideal para llamadas puntuales entre servicios. Compatible con interceptores, error handlers y exchange functions.
WebClient (reactivo)
Para stacks reactivos (WebFlux). No bloqueante, permite composición de flujos y manejo reactivo de errores. Preferible cuando el throughput importa.
Feign Client
Declara la interfaz del cliente HTTP como una anotación Java. Spring Cloud OpenFeign genera la implementación. Simple, legible y integrado con Resilience4j.
Load Balancer
Spring Cloud LoadBalancer distribuye las llamadas entre instancias del servicio obtenidas de Eureka. Sin configuración extra con @LoadBalanced.

gRPC & Protocol Buffers

gRPC es un framework RPC de alto rendimiento de Google. Usa Protocol Buffers como formato binario de serialización, siendo hasta 10x más eficiente que JSON/REST para comunicación interna.

Eficiencia binaria
Protocol Buffers serializa datos en formato binario compacto, reduciendo el tamaño de los mensajes y aumentando la velocidad de serialización/deserialización vs JSON.
Schema-first (.proto)
El contrato se define en un archivo .proto. Se generan stubs de cliente y servidor en múltiples lenguajes. Evolutivo: campos opcionales mantienen compatibilidad.
Streaming bidireccional
gRPC soporta unary, server streaming, client streaming y bidirectional streaming usando HTTP/2. Ideal para observabilidad en tiempo real y feeds de datos.
Cuándo usarlo
Comunicación interna entre microservicios de alta frecuencia. No recomendado para APIs públicas (formato binario dificulta debug) o clientes browser sin grpc-web.

Apache Kafka & Mensajería

Kafka es un log distribuido y tolerante a fallos para comunicación asíncrona entre microservicios. Spring for Apache Kafka simplifica la producción y consumo de mensajes.

Topics & Partitions
Los mensajes se publican en topics divididos en particiones. Cada partición es un log ordenado. El orden está garantizado dentro de una partición, no entre particiones.
Consumer Groups
Múltiples instancias del mismo servicio forman un Consumer Group. Kafka asigna particiones a cada instancia, distribuyendo la carga automáticamente.
Retention & Replay
Kafka retiene mensajes según tiempo o tamaño. Permite re-consumir eventos históricos para reconstruir estado (Event Sourcing) o backfill de nuevos servicios.
Idempotencia
Habilitar exactly-once semantics en Kafka con enable.idempotence=true y acks=all. El consumidor debe ser idempotente: procesar el mismo mensaje dos veces debe dar el mismo resultado.

Event-Driven Architecture

En EDA, los servicios publican eventos cuando algo ocurre en su dominio. Otros servicios reaccionan a esos eventos de forma asíncrona, sin acoplamiento directo.

Domain Events
Hechos que ocurrieron en el dominio: OrderPlaced, PaymentProcessed, ItemShipped. Son inmutables y describen el pasado (tiempo pasado en el nombre).
Event Notification vs Event-Carried State
Notification: el evento solo avisa ("OrderPlaced"). El consumidor consulta el estado. State Transfer: el evento lleva todos los datos necesarios, reduciendo llamadas.
Outbox Pattern
Garantiza que se persiste el estado Y se publica el evento atómicamente. Se escribe el evento en una tabla "outbox" en la misma transacción DB, y un proceso separado lo publica en Kafka.
Schema Registry
Confluent Schema Registry garantiza compatibilidad de schemas (Avro/JSON Schema) entre productor y consumidor, previniendo roturas de contrato en producción.
// Outbox Pattern — persistir y publicar atómicamente
@Transactional
public Order placeOrder(OrderRequest req) {{ '{' }}
  Order order = orderRepo.save(new Order(req));
  outboxRepo.save(new OutboxEvent("OrderPlaced", order.getId(), toJson(order)));
  return order;
{{ '}' }}
// Scheduler publica eventos pendientes en Kafka

Service Discovery (Eureka)

En entornos dinámicos (containers, autoscaling), las IPs cambian constantemente. Service Discovery permite que los servicios se encuentren por nombre en lugar de dirección física.

1
El Eureka Server actúa como registro central. Los servicios se registran al arrancar.
2
Cada servicio envía heartbeats cada 30s. Si falla, Eureka lo elimina del registro tras 90s.
3
Spring Cloud LoadBalancer obtiene la lista de instancias de Eureka y distribuye las peticiones.
4
Alternativas cloud-native: Kubernetes DNS (kube-dns) y Consul para entornos multi-cloud.

@SpringBootApplication

// Llamada con nombre lógico, no IP
@LoadBalanced
RestClient client = RestClient.create("http://inventory-service");

Load Balancing con Spring Cloud

Spring Cloud LoadBalancer reemplaza a Ribbon (deprecado). Permite distribución client-side de carga entre instancias, con algoritmos Round Robin, Random o personalizados.

Client-side LB
El cliente obtiene la lista de instancias del registro y selecciona una localmente. Elimina el single point of failure de un load balancer centralizado y reduce latencia.
Round Robin (default)
Distribuye peticiones de forma equitativa entre instancias. Funciona bien cuando todas las instancias tienen la misma capacidad y las peticiones tienen duración similar.
Health-aware LB
Spring Cloud LB puede excluir instancias no saludables usando el endpoint de Actuator. Evita enrutar peticiones a instancias en proceso de arranque o con problemas.
Kubernetes LB
En Kubernetes, el service DNS y kube-proxy reemplazan a Eureka + Spring Cloud LB. Los Services de K8s proveen balanceo automático sin configuración adicional.
En entornos Kubernetes, considera deshabilitar Eureka y usar el DNS de K8s directamente. Spring Cloud Kubernetes proporciona integración nativa con la API de K8s.
