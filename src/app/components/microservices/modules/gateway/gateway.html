API Gateway con Spring Cloud Gateway

El API Gateway es el punto de entrada único para todos los clientes. Centraliza cross-cutting concerns: autenticación, autorización, rate limiting, routing, load balancing y observabilidad. Spring Cloud Gateway (reactivo, Netty) reemplaza al obsoleto Zuul.

Single Entry Point
Los clientes solo conocen la URL del gateway. El routing interno a los servicios es transparente. Simplifica el descubrimiento de servicios para clientes externos.
Predicates & Filters
Predicate: condición de routing (path, header, method). Filter: transformación pre/post request. Hay 30+ filtros built-in: AddRequestHeader, StripPrefix, CircuitBreaker, RateLimiter.
Reactivo con Netty
Spring Cloud Gateway usa Netty (non-blocking). Puede manejar miles de conexiones concurrentes con pocos threads. Ideal para gateway con alta concurrencia.
Service Discovery
Integra con Eureka/Consul para routing dinámico por nombre de servicio: lb://order-service. Spring Cloud LoadBalancer distribuye entre instancias disponibles.
# application.yml — rutas con predicates y filters
spring.cloud.gateway.routes:
  - id: order-service
    uri: lb://order-service
    predicates:
      - Path=/api/orders/**
    filters:
      - StripPrefix=1
      - name: CircuitBreaker
        args: {{ '{' }} name: orderCB, fallbackUri: forward:/fallback/orders {{ '}' }}
      - name: RequestRateLimiter
        args: {{ '{' }} redis-rate-limiter.replenishRate: 10, redis-rate-limiter.burstCapacity: 20 {{ '}' }}

JWT Centralizado en el Gateway

Centralizar la validación JWT en el gateway elimina la necesidad de que cada microservicio valide tokens. El gateway valida el token, extrae claims y los propaga como headers a los servicios downstream.

1
Cliente envía request con Authorization: Bearer <JWT> al gateway.
2
Gateway filter intercepta y valida la firma del JWT contra la clave pública del Authorization Server.
3
Si válido, extrae claims (userId, roles, tenantId) y los añade como headers: X-User-Id, X-Roles.
4
El request enrutado al servicio downstream incluye estos headers. El servicio confía en ellos (tráfico internal-only).
5
Los servicios internos NO deben ser accesibles desde internet; solo el gateway puede llamarlos.
// Global filter de autenticación JWT
@Component
public class JwtAuthenticationFilter implements GlobalFilter {{ '{' }}
  public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {{ '{' }}
    String token = extractToken(exchange.getRequest());
    Claims claims = jwtValidator.validate(token);
    ServerWebExchange mutated = exchange.mutate()
      .request(r -> r.header("X-User-Id", claims.getSubject()))
      .build();
    return chain.filter(mutated);
  {{ '}' }}

OAuth2 & OpenID Connect

OAuth2 es el protocolo de autorización estándar. OpenID Connect (OIDC) añade autenticación sobre OAuth2. En microservicios, el Authorization Server (Keycloak, Auth0) emite tokens JWT que el gateway y los servicios validan.

OAuth2 (Autorización)
  • ¿Qué puede hacer el cliente?
  • Access Token (opaco o JWT)
  • Scopes: read:orders, write:inventory
  • Client Credentials Flow (M2M)
  • Authorization Code Flow (usuarios)
OIDC (Autenticación)
  • ¿Quién es el usuario?
  • ID Token (siempre JWT)
  • Claims: sub, email, name, picture
  • UserInfo endpoint
  • SSO entre aplicaciones

mTLS entre Microservicios

El mTLS (Mutual TLS) autentica tanto el servidor como el cliente mediante certificados X.509. En microservicios, garantiza que solo servicios autorizados puedan comunicarse entre sí, incluso dentro de la red interna.

TLS unidireccional vs mTLS
TLS normal: el cliente verifica el certificado del servidor. mTLS: el servidor también verifica el certificado del cliente. Autenticación mutua basada en PKI.
PKI interna (CA propia)
Se usa una Certificate Authority interna (cert-manager en K8s, Vault PKI) para emitir certificados a cada microservicio. Los certificados tienen TTL corto y se rotan automáticamente.
Zero Trust Networking
mTLS es el pilar del Zero Trust: "nunca confiar, siempre verificar". Incluso tráfico interno de la red corporativa debe autenticarse. Un servicio comprometido no puede suplantar a otro.
Service Mesh lo gestiona
Istio/Linkerd inyectan un sidecar proxy (Envoy) que maneja mTLS transparentemente. El código de la aplicación no necesita gestionar certificados. PeerAuthentication: STRICT activa mTLS obligatorio.
Con Istio en modo STRICT, todo el tráfico entre pods usa mTLS automáticamente. Sin certificado válido = conexión rechazada. Auditoría completa de quién llamó a quién.

Rate Limiting en el Gateway

El rate limiting en el gateway protege todos los servicios downstream de un solo punto. Redis es el backend estándar para rate limiting distribuido en Spring Cloud Gateway, manteniendo contadores compartidos entre instancias del gateway.

By User (KeyResolver)
Limitar por usuario autenticado: X-User-Id header. Cada usuario tiene su propio contador. Previene que un usuario abuse sin afectar a los demás.
By IP Address
Para endpoints no autenticados, usar la IP como key. Útil para prevenir abuso de endpoints de login o public APIs. CUIDADO: IP puede ser compartida en NAT.
By API Key
Para APIs de terceros, usar el API key del cliente. Cada key tiene su propio tier de límites (free: 100 req/min, pro: 1000 req/min).
Headers de respuesta
El gateway añade headers estándar: X-RateLimit-Remaining, X-RateLimit-Replenish-Rate. Los clientes pueden saber cuántas peticiones les quedan.
// KeyResolver por usuario autenticado
@Bean
KeyResolver userKeyResolver() {{ '{' }}
  return exchange -> Mono.justOrEmpty(
    exchange.getRequest().getHeaders().getFirst("X-User-Id")
  );

Service Mesh con Istio

Un Service Mesh gestiona la comunicación entre microservicios a nivel de infraestructura: mTLS, observabilidad, traffic management y políticas de seguridad, sin modificar el código de los servicios. Istio usa Envoy como sidecar proxy.

Control Plane vs Data Plane
Control plane (Istiod): configura y distribuye políticas a todos los proxies. Data plane (Envoy sidecars): intercepta y gestiona todo el tráfico de red del pod.
Traffic Management
VirtualService: reglas de routing, canary (90/10), A/B testing. DestinationRule: circuit breaker, connection pool, mTLS policy por servicio destino.
AuthorizationPolicy
Políticas fine-grained: "solo el servicio orders puede llamar al servicio payments". Basado en identidad de servicio (SPIFFE/X.509), no en IPs que pueden cambiar.
Observabilidad automática
Métricas HTTP (latencia, error rate, throughput) automáticas para cada servicio. Trazas distribuidas con Jaeger/Zipkin sin instrumentar el código. Golden signals out of the box.
Istio añade latencia (sidecar overhead ~1-3ms por hop) y complejidad operacional. Evalúa si necesitas sus capacidades o si Spring Cloud ya cubre tus necesidades antes de adoptarlo.
