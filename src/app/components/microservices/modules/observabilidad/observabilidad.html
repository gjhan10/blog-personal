Distributed Tracing con OpenTelemetry

El Distributed Tracing permite seguir una petición a través de múltiples microservicios. Un Trace es el viaje completo; un Span es la unidad de trabajo en cada servicio. OpenTelemetry es el estándar unificado que reemplaza a Zipkin y Jaeger específicos.

Trace & Span
Trace: el viaje completo de una petición (e.g., checkout). Span: una operación individual (e.g., "llamada al servicio de inventario"). Cada span tiene traceId (global) y spanId (local).
Context Propagation
El traceId se propaga en headers HTTP: traceparent: 00-{{ '{' }}traceId{{ '}' }}-{{ '{' }}spanId{{ '}' }}-01. Cuando el servicio B recibe la petición, continúa el trace existente como hijo del span del servicio A.
OpenTelemetry
Vendor-neutral. Las trazas se envían al OTEL Collector que las exporta a Jaeger, Zipkin, Tempo o cualquier backend. Cambiar el backend = cambiar la configuración del collector.
Auto-instrumentation
El agente OTEL para JVM instrumenta automáticamente Spring, JDBC, RestTemplate, WebClient sin cambiar el código. Solo configurar el javaagent y el endpoint del collector.
# application.yml — Micrometer Tracing + OTEL
management.tracing:
  sampling.probability: 1.0
management.otlp.tracing:
  endpoint: http://otel-collector:4318/v1/traces
// Span personalizado
@Autowired Tracer tracer;
Span span = tracer.nextSpan().name("process-payment").start();
span.tag("payment.amount", amount.toString());
span.end();

Logging Centralizado con ELK Stack

Con decenas de microservicios, los logs deben centralizarse para poder correlacionarlos y buscar por traceId. ELK (Elasticsearch + Logstash + Kibana) o la alternativa moderna Grafana Loki son las soluciones estándar.

Elasticsearch
Motor de búsqueda y almacenamiento de logs. Indexa los logs en tiempo real. Permite búsqueda full-text y consultas complejas por cualquier campo del log estructurado.
Logstash / Filebeat
Logstash: procesamiento de logs (parsing, enrichment, filtrado). Filebeat: colector ligero que lee logs de archivos y los envía a Elasticsearch directamente o vía Logstash.
Kibana
Visualización y búsqueda de logs. Dashboards de error rate por servicio, búsqueda por traceId para ver todos los logs de una petición, alertas cuando error rate supera umbral.
Structured Logging (JSON)
Los logs deben ser JSON estructurado: nivel, mensaje, traceId, spanId, servicio, timestamp. El traceId permite correlacionar logs de múltiples servicios de la misma petición.

Health Checks, Liveness & Readiness

Kubernetes usa los health probes para gestionar el ciclo de vida de los pods. Liveness: ¿está vivo el proceso? Readiness: ¿puede recibir tráfico? Spring Boot Actuator expone /actuator/health/liveness y /actuator/health/readiness.

Liveness Probe
  • ¿Está el proceso funcionando?
  • Si falla → Kubernetes reinicia el pod
  • Para deadlocks, OOM, estados corruptos
  • No incluir dependencias externas
  • Solo el estado interno del proceso
Readiness Probe
  • ¿Puede recibir tráfico?
  • Si falla → K8s quita del load balancer
  • Para inicialización, dependencias, warm-up
  • Puede incluir DB, cache, etc.
  • Pod sigue vivo pero sin tráfico
# Kubernetes probe configuration
livenessProbe:
  httpGet: {{ '{' }} path: /actuator/health/liveness, port: 8080 {{ '}' }}
  initialDelaySeconds: 30
  periodSeconds: 10
readinessProbe:
  httpGet: {{ '{' }} path: /actuator/health/readiness, port: 8080 {{ '}' }}
  initialDelaySeconds: 10
  periodSeconds: 5

Redes de Docker

Kubernetes para Microservicios

Kubernetes es el estándar para orquestar microservicios en producción. Proporciona self-healing, escalado automático, rolling deployments y service discovery. Los recursos clave son: Deployment, Service, ConfigMap, HPA e Ingress.

Deployment & ReplicaSet
El Deployment define el estado deseado (imagen, réplicas, resources). Kubernetes garantiza que siempre haya N réplicas corriendo. Rolling update: actualiza pods gradualmente sin downtime.
Service & ClusterIP
Un Service provee un IP estable y DNS para acceder a los pods. ClusterIP: interno al cluster. NodePort: expone en cada nodo. LoadBalancer: provisiona un LB externo (cloud).
HPA (Horizontal Pod Autoscaler)
Escala automáticamente el número de pods según métricas: CPU, memory o métricas custom (req/s desde Prometheus). Reacciona a picos de tráfico sin intervención manual.
ConfigMap & Secrets
ConfigMap: configuración no sensitiva. Secrets: credenciales cifradas (base64, integrar con Vault). Inyectados como variables de entorno o volúmenes en los pods.

        name: cpu
