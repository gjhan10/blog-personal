19M4 · CQRS & Event Sourcing

CQRS Fundamentos

Command Query Responsibility Segregation (CQRS) separa el modelo de escritura (Commands) del modelo de lectura (Queries). Cada lado puede escalar, optimizarse y desplegarse de forma independiente.

Command Side
  • Modifica el estado del sistema
  • Valida reglas de negocio
  • Modelo rico en comportamiento (Domain Model)
  • Optimizado para consistencia
  • Generalmente normalizado (relacional)
Query Side
  • Solo lectura, nunca escribe
  • Modelo aplanado, desnormalizado
  • Optimizado para velocidad de consulta
  • Puede usar proyecciones en Redis, Elasticsearch
  • Consistencia eventual desde el Command side
Command
Intención de cambiar el estado: CreateOrderCommand, ShipOrderCommand. Son inmutables, validados en el command handler. Pueden ser aceptados o rechazados.
Query
Solicitud de datos sin efectos secundarios: GetOrderByIdQuery, FindOrdersByUserQuery. Retornan DTOs optimizados para la vista, no entidades de dominio.
Escalado independiente
En la mayoría de sistemas, las lecturas superan a las escrituras 10:1 o más. Con CQRS, puedes escalar el query side horizontalmente sin afectar el command side.
Consistencia eventual
El query side se actualiza asíncronamente tras un comando. Hay un pequeño lag entre escritura y lectura. El sistema diseña en torno a esta realidad, no contra ella.
20M4 · CQRS & Event Sourcing

Command Side con Spring

El command side implementa el modelo de dominio rico. Los command handlers son el punto de entrada, validan el comando, interactúan con el agregado y publican eventos de dominio.

// Command inmutable
public record CreateOrderCommand(UUID orderId, UUID userId, List<OrderItemDto> items) {{ '{' }}{{ '}' }}
// Command Handler
@Service
public class CreateOrderCommandHandler {{ '{' }}
  private final OrderRepository repo;
  private final ApplicationEventPublisher events;
  @Transactional
  public void handle(CreateOrderCommand cmd) {{ '{' }}
    Order order = Order.create(cmd.orderId(), cmd.userId(), cmd.items());
    repo.save(order);
    events.publishEvent(new OrderCreatedEvent(order));
  {{ '}' }}
{{ '}' }}
Los command handlers deben ser transaccionales. El evento se publica dentro de la transacción para garantizar que si el guardado falla, el evento no se propaga.

Query Side y Proyecciones

Las proyecciones son vistas materializadas del estado actual, construidas escuchando eventos de dominio. Pueden almacenarse en cualquier store optimizado para el caso de uso: Redis para caching, Elasticsearch para búsqueda full-text, bases de datos SQL desnormalizadas para reportes.

// Proyección: escucha OrderCreatedEvent y actualiza la vista de lectura

22M4 · CQRS & Event Sourcing

Event Sourcing

En lugar de guardar el estado actual, Event Sourcing guarda la secuencia de eventos que llevaron a ese estado. El estado se reconstruye reproduciéndolos. Proporciona un audit log completo, capacidad de "viajar en el tiempo" y reconstrucción de proyecciones.

Base de datos tradicional
  • Guarda el estado actual
  • UPDATE sobrescribe datos anteriores
  • Sin historial de cambios
  • Difícil auditoría
  • Consultas simples
Event Sourcing
  • Guarda cada cambio como evento inmutable
  • APPEND-only, nunca sobrescribe
  • Historial completo siempre disponible
  • Auditoría gratuita
  • Reconstrucción de estado en cualquier punto temporal
// Reconstruir estado aplicando eventos
public Order reconstitute(List<DomainEvent> events) {{ '{' }}
  Order order = new Order();
  events.forEach(order::apply);
  return order;
{{ '}' }}
23M4 · CQRS & Event Sourcing

Saga Pattern

Una Saga coordina transacciones distribuidas a través de múltiples microservicios. Dado que las transacciones ACID no existen entre servicios, una Saga es una secuencia de transacciones locales con compensaciones en caso de fallo.

Choreography
Cada servicio escucha eventos y reacciona publicando sus propios eventos. Sin coordinador central. Más desacoplado pero difícil de visualizar el flujo completo.
Orchestration
Un orquestador central (Saga Orchestrator) dirige el flujo enviando comandos a cada servicio y reaccionando a sus respuestas. Más visible y controlable.
Transacciones compensadoras
Si el paso N falla, se ejecutan las transacciones compensadoras de los pasos N-1 a 1. No son rollbacks; son operaciones de negocio inversas que devuelven el sistema a un estado coherente.
Saga de creación de orden
1. Crear orden → 2. Reservar inventario → 3. Procesar pago → 4. Confirmar envío. Si pago falla → cancelar reserva → cancelar orden.
Las Sagas solo garantizan consistencia eventual, no ACID. El diseño debe asumir que los pasos son visibles en estados intermedios. El sistema debe manejar idempotencia en cada paso.
24M4 · CQRS & Event Sourcing

Axon Framework

Axon Framework es la implementación Java más completa de CQRS + Event Sourcing + Saga Pattern. Proporciona anotaciones que mapean directamente a los conceptos del dominio: @Aggregate, @CommandHandler, @EventSourcingHandler, @SagaEventHandler.

// Agregado con Event Sourcing en Axon
@Aggregate
public class OrderAggregate {{ '{' }}
  @AggregateIdentifier private UUID orderId;
  private OrderStatus status;
  @CommandHandler
  public OrderAggregate(CreateOrderCommand cmd) {{ '{' }}
    AggregateLifecycle.apply(new OrderCreatedEvent(cmd.getOrderId()));
  {{ '}' }}
  @EventSourcingHandler
  public void on(OrderCreatedEvent event) {{ '{' }}
    this.orderId = event.getOrderId();
    this.status = OrderStatus.CREATED;
  {{ '}' }}
{{ '}' }}
Axon Server actúa como Event Store y Message Router. En producción, Axon Server EE ofrece clustering, multi-tenancy y contextos segregados por bounded context.
